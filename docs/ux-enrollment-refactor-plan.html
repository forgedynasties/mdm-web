AIO MDM · dashboard · stage-dpc

Mixed fleet UI/UX refactor

Make the dashboard treat firmware devices and DPC-managed outsourced devices as one fleet, with enrollment as a visible lifecycle and every control derived from what the device can actually do.

Status proposal, nothing implemented Written 2026-09-08 Branch stage-dpc at 861dc95 Agent mdm-dpc-agent at d5e5c81 Source docs/ux-enrollment-refactor-plan.md

0 · Why

The server's business logic and every dashboard page were designed for one situation: every device is our own hardware (T7, later Kiosk 18/22/27), runs our firmware plus the com.aioapp.mdm system-app client, authenticates with one shared DEVICE_API_KEY, and "enrolls" itself by checking in for the first time (UpsertCheckin → isNew → notifyDeviceOnboarded). There was no enrollment concept because there was nothing to decide: a serial appeared, it was ours, it was a T7.

That is no longer true. The fleet now also contains outsourced Android hardware (kiosks, mPOS, POS terminals) running the Device-Owner DPC agent com.skorra.agent. Those devices:

  • are heterogeneous: any manufacturer, model, form factor;
  • must be explicitly enrolled: profile token or QR → POST /api/v1/enroll → per-device dvk_… key;
  • support a different and variable command set: no screenshot, has wipe, capabilities advertised in extra.capabilities;
  • need site, group and policy assignment as part of onboarding, not as an afterthought.

The DPC work already landed on stage-dpc: enrollment profiles, deviceAgentInfo, a capability-aware device page, DPC tags in the Actions console, a product catalog with generic caps for unknown products, and policy, compliance and network pages. But it was bolted onto the firmware-era information architecture, and the pieces that would make it a coherent product are hidden from the nav (commits 1fac252, e242ab8, 7ca83d5). The dashboard still reads as "a T7 fleet with some odd devices in it".

Thesis

This plan makes the mixed fleet the first-class mental model of the dashboard.

1 · Goals, non-goals, principles

Goals

  1. One dashboard, one design language (docs/ui-design-language.md), for both device kinds. No "DPC section" and "firmware section".
  2. Enrollment becomes a visible lifecycle: how does a device get here, what is it, who does it belong to, is it healthy, how does it leave. This applies to firmware devices too, even though their enrollment is automatic.
  3. Every control the UI shows is derived from what the device can actually do (capability-driven), not from which page it is on.
  4. Zero regression for the deployed firmware fleet: shared-key auth, auto-onboarding, T7 defaults, OTA and release matching keep working unchanged.

Non-goals

  • Replacing shared-key auth for firmware devices with per-device keys. That is a client OTA project; the UI only needs to show which auth a device uses.
  • Android Enterprise zero-touch or Google EMM registration. QR and adb provisioning only.
  • Redesigning pages unrelated to fleet composition: Releases, Alerts config, Users.

Replace the two call sites of deviceAgentInfo (handlers.go around lines 5055 and 12108) and CountDPCDevices (db.go 3269) with the column. Keep deviceAgentInfo only as the ingest parser.

2.2 enrollment_profiles table

Add device_class, restaurant_id (site), policy_id (kiosk or policy preset applied on enroll), expires_at, max_enrolls, created_by, last_enrolled_at. EnrollDevice applies class, site and group; if all three are set the device is auto-onboarded.

2.3 Product catalog

  • Add Kind (firmware or android) and Class to Product. Catalog entries stay hard-coded for our hardware. Unknown products (the Resolve fallback) get kind android and class from the device row, not the catalog.
  • Add Caps fields only where hardware truth matters and the agent cannot report it; HasWLC is the model. Everything the DPC agent can report (screenshot, shell, kiosk lock, wipe, app install, managed config, network provisioning) comes from devices.capabilities.
  • Firmware clients do not send capabilities today. Define a static default capability set per firmware product (product.DefaultCaps(key)) so the same gating code path works for both kinds. When the firmware client later reports capabilities, reported wins.

2.4 Capability → command table

Single source of truth, new file internal/product/caps.go or internal/dashboard/capability.go:

// what a command type needs; empty = always allowed.
// Names match mdm-dpc-agent Capabilities.kt so the agent's list is used verbatim.
var commandNeeds = map[string]string{
    "screenshot":    "screen_capture", // dpc: degraded (MediaProjection consent)

    "shell":         "shell",          // dpc: degraded (unprivileged sh)
    "logcat":        "logcat",         // dpc: degraded (app-scoped)
    "ota":           "ota",            // firmware only
    "update_splash": "update_splash",  // firmware only
    "wipe":          "wipe",           // dpc only
    "kiosk_set":     "kiosk",
    "managed_config":"config",
    "mic_gain_read": "mic_gain",       // T7 only (product cap)
    "wlc_set":       "wlc",            // T7 only (product cap)

func (d Device) Supports(cmdType string) bool   // full support
func (d Device) Degraded(cmdType string) bool   // works with limits; UI shows a note
Agent change needed

The agent today sends only its supported list (kiosk, install_apk, uninstall, reboot, wipe, config, telemetry). Its degraded list (screen_capture, input, logcat, shell) stays on the device. Also send capabilities_degraded so the dashboard can show "works with limits" instead of "unavailable". Until then absent means unsupported.

Exposed as template func supports .Device "screenshot" and used by: device page action menu, Actions console target resolution and impact panel (CommandImpact), bulk command send (enforceCommandTargets drops unsupported devices with a reason), alert rules (skip devices lacking the metric), and Policies targeting. Today this logic exists as ad-hoc IsDPC checks in three places.

2.5 Events

Emit device events for enrolled, re_enrolled (key rotated), onboarded, retired, wiped, profile_revoked. The device page timeline and the Activity page show them; the Overview inbox counts them.

3.3 Fleet → Enroll (redesigned Enrollment page)

Three stacked zones, built with cc-*.

  1. Inbox: needs assignment. Rows where onboarded_at IS NULL: serial, model, kind, class, source (profile name or "firmware auto-enroll"), enrolled at, inline site and group selects, Done. Bulk select → assign → Done. Live: subscribe to the WS device-update channel (PublishDeviceUpdate already fires on enroll) so a scanned device appears within a second while the tech is standing there. Same zone appears as the Overview widget.
  2. Enrollment profiles. Cards instead of a table: name, class, site, group, policy, enrolled count, expiry, status, QR button (existing qr.png route), token copy. Create through a 3-step drawer (identity → assignment → policy and expiry) instead of the inline form. Revoke, reactivate and delete stay.
  3. How devices get here. Collapsed by default, three tabs: QR provisioning (factory reset, tap 6×, scan), adb (existing steps, generated with the selected profile's token instead of the shared key), Firmware devices (explains automatic enrollment via the shared device key, with key mask and copy for admins). The shared key stops being presented as "the" agent credential; it is the firmware credential.
Blocking state

If AGENT_APK_URL and AGENT_APK_CHECKSUM are not set, profile cards show a QR cold-provisioning off tag linking to Settings → Agent APK, instead of today's inline warning paragraph.

3.4 Device page

  • Identity ribbon: hardware model (exists) · kind tag Firmware or DPC agent (replaces the tooltip-only ddc-dpc-tag) · class tag · enrollment state tag New Retired Wiped. Firmware devices get a tag too so the two kinds look symmetric.
  • Actions menu built from supports: unsupported items render disabled with a reason (pattern already used for screenshot on DPC); a section is omitted entirely when none of its items apply.
  • New sidebar card "Enrollment": source (profile link or "auto, firmware"), enrolled at, key type (shared or per-device, rotated at), inline site, group and class assignment, buttons Mark onboarded, Rotate key (DPC: forces re-enroll on next check-in), Retire (sets status, hides from active views, keeps history), Wipe (DPC, admin; moves here from the actions menu with the existing confirm copy).
  • Capability-gated cards already exist for battery, charging and WLC via product caps. Extend the same pattern: the Kiosk card shows DPC lock-task mode vs firmware kiosk config; the Apps card shows managed-config controls only when the managed_config capability is present.
  • Timeline gains the 2.5 events.

3.5 Actions console

  • Target rail filters: kind, class, capability ("devices that support install_apk").
  • Impact panel: "18 selected · 14 support this action · 4 skipped (2 firmware: wipe unsupported, 2 offline)". The send path drops unsupported devices and the history row records the skip reason per device.
  • The action list is filtered by the selection: choose 3 mPOS terminals and OTA and splash disappear, wipe appears.

3.6 Policies

Un-hide /manage as one tabbed page. Each policy declares applies_to (kinds, classes) and the form shows only fields the target can honour. Coverage headline stays ("2 policies cover 18 of 26 devices") but the bar is split by kind so it is obvious when a policy cannot reach firmware devices.

4 · Enrollment flows, end to end

AFirmware device

Unchanged mechanics, new presentation.

first check-in, shared key→row: firmware · auto · class from product→inbox "auto-enrolled"→operator assigns site + group→Done

If the serial was pre-listed on a staged-devices list (optional, phase 6) with a site, it is auto-onboarded.

BDPC device, QR

admin creates profile (class, site, group, policy, expiry)→print QR→factory reset, tap 6×, scan→agent installs as Device Owner, calls /enroll→profile applied, PublishDeviceUpdate→row appears live, assigned, auto-onboarded

Tech sees "Enrolled · mPOS · Site X" on the dashboard and on the agent screen.

CDPC device, adb or manual token

Same as B. The adb tab renders commands with the chosen profile's token.

DRe-enrollment after factory reset

Same serial hits /enroll: key rotates, key_rotated_at set, event re_enrolled, site, group and history kept. Inbox does not re-open unless the profile differs in class or site.

ELeaving

Retire (both kinds): status retired, hidden from default Fleet views, excluded from alerts and policy coverage, visible under Status = Retired. Wipe (DPC): command, then status wiped on ack. Revoke profile: existing devices unaffected, copy says so.

FFailure states to design, not just handle

Expired or revoked token scanned: agent shows the reason, profile card shows "3 rejected attempts in the last hour". Enrolled but never checked in: inbox row says "enrolled 10 min ago · no telemetry yet" with a wifi hint. Check-in from a retired serial: auto-unretire plus event.

6 · Open questions and assumptions

  1. DPC agent source: resolved. ~/mdm-kiosk/mdm-dpc-agent (main, com.skorra.agent). Facts that shape the plan: product is Build.PRODUCT, a codename and not a form factor, so class must come from the profile (Q2). Telemetry carries manufacturer, model, serial, security posture and location. The agent's status screen shows Device Owner state, serial and connection, with one credential field that accepts enr_… tokens. Remaining ask: an enrollment result state on that screen ("Enrolled · mPOS · Site X") fed by the /enroll response, which today returns only device_key. Extend the response with class, site, group and profile.
  2. Class for outsourced devices comes from the enrollment profile, not the hardware. Alternative: a model → class mapping table maintained by admins. Profile-first is simpler and matches how batches are rolled out; keep the admin override on the device.
  3. Naming. "Restaurants" is the existing site concept. "Sites" in copy only if non-restaurant customers are expected; routes and DB names unchanged either way.
  4. Firmware device capabilities are static per product until the firmware client reports them. An OTA of a client that sends capabilities is out of scope here.
  5. mPOS and POS specific controls (payment app managed config, printer status) are not designed here; they become capability-gated cards once the agent advertises them.
  6. Retire vs hidden. devices.hidden exists today. Proposal: retired is a lifecycle status shown in the UI; hidden stays the admin-only "pretend it does not exist" flag.
