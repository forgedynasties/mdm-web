01

How a device talks to the server

Three transports, for three different reasons. The split matters because each has a different failure mode, and the storage design follows from which one a device is using.

TransportCarriesWhenNote
POST /api/v1/checkina full snapshot (keyframe)~5 minthe safety net: works through anything that survives a plain HTTP request
GET /api/v1/wsdelta frames up, commands downlivethe normal path. A frame is sent only when a gated field actually moves
GET /api/v1/remote/{serial}H.264 screen + inputon demandone session per device; a second viewer takes over the first
otautil, port 8000legacy OTA polling15 mina second listener. The IP is baked into pre-agent firmware, so the port is a contract that cannot be changed
Both ingest paths are one function

HTTP and WebSocket used to be maintained separately, which is exactly how they drifted: the WS path had no OTA capability gate, so a build that could not apply an update was handed one anyway, and it never asked for an app list, so a re-flashed device showed its old apps indefinitely. Both had been quietly true for as long as the two paths existed. Collapsing them onto one ingestCheckin is what surfaced them — the refactor was worth more than the 37 lines it saved.

02

What happens to a check-in

The one thing the write path still reads

The store-or-skip decision used to compare the incoming report against the previous stored row’s snapshot. Retiring that column would have made the comparison false for every report, so every report would store a row — multiplying the write volume the whole exercise exists to cut, with nothing appearing broken. Hence state_hash: the row keeps a digest of exactly the projection that comparison made, and nothing else.

03

Where it all lives

Fifty-odd tables; six matter for size. Everything else is configuration, identity and bookkeeping measured in kilobytes.

Numbers → device_samples

Battery, temperature, RAM used and total, free storage, Wi-Fi signal. Fixed columns keyed (device_id, at) — the order every reader wants, so it needs no second index, and each insert lands at the right edge instead of dirtying a random page. 91 bytes of heap, 73 of index.

States → device_state_events

Charging, pad status, screen, Wi-Fi, IP, timezone, boot. One row per real change, plus one seed recording a value the first time it is seen. Nothing at all is written while a state holds, so an idle device costs nothing here.

Where the next saving is

Indexes are now the majority of the cost — 211 bytes of the 444 a stored report takes, against 233 of heap. The payload got small enough that finding it costs more than storing it. And checkins is close to redundant: it spends ~280 bytes a row on battery_pct, build_id and state_hash, while device_samples already holds the battery reading and the timestamp and device_build_history holds build changes. Its only irreplaceable column is the hash that decides whether to write the row at all.

04

The queue that does exist

Nothing queues on the way in. Everything queues on the way out — because a command must survive a device being asleep, offline or mid-reboot, and a check-in must not.

TableHoldsWhy it is durable
commandsthe instruction and its payloada device offline for a day must still get its install when it returns
command_targetswho it was aimed atone command, many devices, resolved from groups at send time
command_statusper-device delivery statequeued → delivered → received → done, with receipt-ack from the client
command_resultswhat came back171 MB for 5,100 rows — nearly all TOASTed output blobs

Flushed on connect, after every ack, and once a minute. Commands expire by type — minutes for a reboot, a day for an install — so a stale instruction cannot surprise a device that has been away. A dropped WebSocket push costs nothing: the queue re-delivers it.

Every one of these moved one at a time

Each reader was diffed against the old source on real data before the next was touched — 622 alert fires against 622, a rollup compared column by column across 80 devices, a CSV asserted cell for cell. That discipline is the only reason the snapshot could be retired at all: these failures are silent by nature. An alert that never fires and a chart that renders empty look exactly like a fleet with nothing wrong.

Why every one of them has a row cap

The strip job shipped with a wall-clock deadline and no effective row cap. Its first run rewrote 295,161 rows in under four minutes and a Postgres backend was OOM-killed shortly after. A deadline bounds how long you spend, not how much you rewrite — and on a 2 GB instance that distinction is the difference between a background job and an outage.

The failure this box is actually prone to

Postgres backends were OOM-killed 17 times in three days, and not by heavy queries. A backend never returns memory to the OS after a query, so with idle connections held for 30 minutes, one burst of dashboard fan-out left 59 of them holding 1.72 GiB of a 2 GiB limit with nothing running. Anything that adds sustained memory pressure here — a browser, a large rewrite, an unbounded aggregate — should be assumed to take the database down until the instance is resized.
