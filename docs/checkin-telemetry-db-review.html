AIO MDM · check-ins · telemetry · database

25.2 million check-in rows, 15 GB, and the top device writes one every nine seconds.

The senior dev asked four questions about the MDM server: is there a queue, what are the server specs, what are the DB specs, and how much data 100 idle devices produce in an hour. Those answers are below, together with his follow-up advice and a fresh audit of the live box that says the idle footprint is no longer the main problem — duplicate writes are.

The headline finding. Coalescing is supposed to hold an unchanged device to one row every 30 s. The six busiest devices are averaging a row every 9–14 s, and the smallest gap between two rows for one device is 5.8 milliseconds. Two independent code paths are writing the same snapshot, and a goroutine leak makes the server ask for that snapshot more than once per interval. Retention has never been switched on, so every one of those rows is still there.

His four questions, answered

1. Is there a queue in the server?

No broker. No Redis, NATS, Kafka or SQS. The device → server path is fully synchronous: POST /api/v1/checkin → internal/api/handlers.go:704 → db.UpsertCheckin (internal/db/db.go:1424) → one Postgres transaction → response. Go's net/http gives one goroutine per request, unbounded. There is no worker pool anywhere.

There is a durable queue in the other direction. Server → device commands live in Postgres (commands, command_targets, command_status) with receipt-ack, client-side id dedup and per-type expiry — 5 min for quick actions, 24 h for installs. It is flushed on connect, after each ack, and every minute, so it survives an offline device.

A dropped WS push is not lost work: the Postgres command queue re-delivers it. A dropped dashboard event only costs a live UI refresh.

What he advised next

  • Turn retention on. checkin_retention_days is 0, meaning keep forever. Setting 30–60 is config-only, no code.
  • Partition checkins by month. A retention DELETE over tens of GB on 2 vCPU and 3000 IOPS will hurt; DROP PARTITION is free.
  • Raise checkin_sample_sec to 60–120. Transitions still land instantly; only the idle heartbeat thins out.
  • Watch pool vs max_connections. 60 pool conns against 100 max is fine for one instance, not for two.
  • Past ~500 devices needs an external session/rate-limit store and WS fan-out over LISTEN/NOTIFY or Redis before it can go multi-replica.
  • Move off t2. t3.medium is the same size, cheaper, with better burst behaviour.

Fresh findings, 17 September

The same snapshot is written twice, and asked for more than once

Three independent mechanisms multiply the write rate:

  1. Dual-transport writeHTTP Checkin (handlers.go:704) and WS HandleWsTelemetry (handlers.go:1397) are two hand-maintained copies of the same logic writing the same tables. HTTP stores a full keyframe (mergeExtra=false), WS merges a delta (mergeExtra=true). Because coalescing compares the new extra against the previous stored row, alternating keyframe and delta shapes reads as a change every time — so the 30 s floor never applies.root cause
  2. Leaked telemetry-request loopsConnect() spawns go h.runTelemetryRequestLoop(deviceID) on every WS upgrade (handlers.go:178) with no context, no cancel map and no check for an existing loop. hub.Push keys on device id only, so after a fast reconnect the old loop keeps succeeding against the new connection and never exits. A device that flaps N times inside one interval ends up with N loops, each asking for telemetry on its own timer. Confirmed by reading the code; matches the 5.8 ms row gaps.root cause
  3. DPC agent sends everything, always30 s HTTP loop plus a WS send on connect and on every telemetry_request, both built from the same buildCheckin(), with no dedup between transports and no field-level diffing — only a CRC32 apps-hash gate on the installed-apps list. The firmware kiosk client, by contrast, skips the send entirely when no gated key changed, and its HTTP leg is a 5-minute safety net.3 devices today, the whole fleet later

The third item is the one that scales badly: the mixed-fleet work puts DPC agents on every new device, at roughly ten times the firmware client's write rate.

Smaller things the audit turned up

  • A check-in is not atomic. Only UpsertCheckin is in a transaction (3 statements). Device events, packages, OTA state, config and command acks are separate non-transactional calls in the same handler.
  • Idle is not free. Recent-tier alerts run every minute over the whole fleet, hourly housekeeping rolls up device_daily_stats and re-evaluates alerts, five redrive jobs run every minute. An idle fleet still writes.
  • No migrations directory. The whole schema is one embedded idempotent SQL string in db.go (~10225–11566), which is why partitioning has to be planned as a deliberate migration rather than a DDL edit.
  • Single-instance state: WS client map, presence and throttle maps, seven subscriber channel sets, the per-serial rate limiter, remote-control sessions and tokens, the OTA verdict cache. Two replicas behind an LB would each see half the fleet.
  • Retention exists but is off for check-ins and logcat. Resolved alerts do prune at 90 days.
  • wifi_ap_locations took 19,065 updates on 769 rows — worth a look after the bigger items.

Two design changes on top

Both come from the same observation: the table stores a full snapshot on a timer, when what anyone actually reads back is either when something changed or a number over time.

Store transitions, not snapshots

Today a wireless-charging status flip writes a whole 600-byte row carrying every other field alongside it, and the next 30-second sample writes them all again. What the WLC feature needs from history is a list of changes with their timestamps — on at 11:04, off at 11:41 — which is roughly 60 bytes per real event and nothing at all while the state holds.

That splits the current single table into three things, each shaped like its reader:

The comparison that decides a transition already exists — it is the coalescing check in UpsertCheckin (db.go:1544-1561) that today's code uses only to decide whether to write a snapshot. It would write an event row instead.

One transport at a time

A device with a live WebSocket does not need its HTTP check-in stored as well — that is the duplicate write from the findings above, seen from the client side. The server can already answer the question: h.hub.IsConnected(deviceID).

It cannot be dropped outright. The HTTP call is the only keyframe — it stores with mergeExtra=false, replacing latest_extra wholesale, which is what clears keys a device has stopped sending. WS frames merge (mergeExtra=true), so a device that only ever sent deltas would accumulate stale keys forever and never correct them. So the rule is demotion on a timer, not deletion.

The rule

ConditionStoreStill does
No live WSeverything unchangedthe current path, untouched
WS live, last keyframe older than http_keyframe_min_seceverythingrefreshes the keyframe clock
WS live, keyframe still freshnothingreturns config, policy and pending commands as usual
Payload carries installed_appseverythingnever skipped; the app inventory only rides HTTP
Payload carries ota_progresseverythingnever skipped; a rollout in flight outranks the saving

Default http_keyframe_min_sec = 0 (off). Turn it on at 900 after watching one fleet-day. For the DPC agent that is 120 stored keyframes an hour down to 4; for the firmware client, 12 down to 4.

What it needs

  • A serial → device id lookup before the write. Today the handler learns the id from UpsertCheckin itself, so it cannot ask the hub anything yet. 193 devices: a small cached map, or the unique index on serial_number, which is a cheap hit either way.
  • A last-keyframe clock, one timestamp per device, in process memory beside the hub. No schema change. An empty map after a restart means the first HTTP call per device stores — which is the behaviour you want anyway.
  • A liveness test stronger than "registered". hub.IsConnected is true while the client object exists, and a half-open socket can outlive the device. Prefer "a frame was received from this device recently" over "a socket is registered", or accept that the keyframe floor bounds the damage to 15 minutes.
  • A counter for skipped keyframes at /debug/vars, so the saving is visible and a device stuck in skip-mode is findable.

What it does not break

The obvious worry is presence: skipping the write means devices.last_seen_at goes stale while the device is plainly alive, which would normally light up every offline alert in the fleet. That is already handled — the offline queries explicitly exempt a device with a live WebSocket (db.go:9245, db.go:9529: "A device with a live WebSocket is NOT offline, even if its last_seen_at has gone stale"). The same condition that makes the write skippable is the one that keeps the device online. Worth re-reading both queries before shipping, since the whole design leans on them.

The firmware client already behaves this way by itself — WS deltas, HTTP only as a 5-minute safety net — so this rule barely touches it. The DPC agent posts a full snapshot every 30 seconds regardless, and is the reason to do it server-side: agents already in the field cannot be updated on demand, and the database should not depend on every agent being well-behaved.

Status, 18 September

His first question, asked again: is there a queue now? No — and deliberately not. There is still no broker, no Redis or NATS, and no worker pool: a check-in is still POST /api/v1/checkin → ingestCheckin → UpsertCheckin → one Postgres transaction → response. What changed is the size of that transaction. The row it writes went from 937 bytes to about 71, the snapshot it used to store is gone, and the fleet stores 52,000 rows a day instead of 118,869. A queue absorbs work you cannot make smaller; this work got smaller. The durable queue in the other direction — server → device commands in Postgres, with receipt-ack and per-type expiry — is unchanged and still the thing carrying the load that actually needs a queue.

He was right about the pool, for a reason neither of us had found. "Watch pool vs max_connections" read as a headroom warning. It was actually the cause of an outage pattern this audit never diagnosed: Postgres backends were OOM-killed 17 times between 16 and 18 September. Not from heavy queries. MaxConnIdleTime was 30 minutes against MaxConns 60, and a Postgres backend never returns memory to the OS after a query — so one burst of dashboard fan-out grew the pool to 60 and every idle connection then held whatever its largest query had needed. Measured with nothing running: 59 idle connections, 1.72 GiB of non-reclaimable anonymous memory against a 2 GiB limit, page cache only 221 MB. Idle connections are now reaped in 90 seconds and the lifetime halved; MaxConns stays at 60 because the fan-out that needs it is real. After: 6 idle connections, 216 MB anon, the container at 412 MB of 2 GiB, and no kill since.

The part he did not ask for

Storing telemetry by shape rather than as one snapshot per report was not on his list, and is the change the rest rests on. Numbers go to device_samples in fixed columns; states go to device_state_events, one row per real change, so an idle device costs nothing. Every reader moved across one at a time, each diffed against the old source on real data before the next: the chart, the SSE payload, five alert rules, charger-flap detection, the CSV export, the daily rollup, the device page and the public API. Then checkins.extra stopped being written.

Two things that only a diff would have caught. The state stream had no baseline — the writer recorded a key only when it changed, comparing against a snapshot that already held every value, so no device existing at the time ever got a first event: timezone had 0 events against 150 devices reporting it. And the store-or-skip decision on the write path read the snapshot it was about to stop storing; emptying the column would have made every report store a row, multiplying the write volume the work exists to cut. Neither would have failed loudly.

What to tell him in one line. The idle-footprint answer he asked for was right, but it described the design, not the deployment: retention was never enabled, two write paths defeated the coalescing the estimate assumed, and a reconnect bug multiplied the request rate. All three are fixed, and the table has stopped growing — not by enabling retention, which was rejected because no day may be deleted, but by storing telemetry by shape and downsampling old history. Still open from his list: the DPC agent diff, and moving off t2 with Postgres tuned to match. Partitioning is written and rehearsed but parked, because the two things it was wanted for — cheap retention and dropping the dead primary key — turned out not to need it.
