Executive summary

A capable, security-conscious fleet platform — one operational lap from production.

AIO MDM is a full mobile-device-management stack — a Go control plane, a real-time dashboard, and a root-privileged Android agent — already running a real fleet of roughly 900 devices. The product surface is deep and genuinely wired to live data. The remaining distance to "production-grade" is operational discipline — tests, backups, high-availability — not a security or feature rewrite.

How it's built

One lean Go binary, three surfaces, one real-time spine

No web framework and few dependencies — a deliberately minimal, current stack. A single process serves the device fleet, the admin API, and the operator dashboard, backed by PostgreSQL and an in-process real-time hub that pushes updates to browsers and devices alike.

The device agent

Root-equivalent control of every device

The Android client is an AOSP system app — platform-signed, sharing the system UID, and self-provisioning as Device Owner. In practice there is no capability ceiling: it can install, wipe, watch, drive, reboot, and re-flash a device. The runtime engineering behind it is mature and clearly battle-tested.

Privilege posture

Maximum short of root

Platform signature + android.uid.system + Device Owner. Silent app management, input injection, screen capture, firmware flashing, and shell as the system user are all on the table. This is real MDM power — and it makes the server's trust model the thing that matters most.

Security posture

A real pen-test — and the findings were taken seriously

The team commissioned an independent third-party penetration test (TSAI, June 2026): 44 pages, 20 findings, OWASP + NIST methodology. The headline was a Critical authorization flaw — and a review of the current code shows it and the top High findings already remediated a month later. For a system at this stage, that's an above-average security story to tell.

Controls the testers credited

  • TLS 1.0 / 1.1 correctly rejected
  • HMAC-signed, tamper-resistant session cookies
  • Constant-time login — no user enumeration
  • No SQL injection; path traversal normalized
  • Auth checked before request parsing
  • Admin vs. device API-key separation
  • WebSocket rejects session cookies

The foundations were sound; the flaw was authorization depth. That's the good kind of finding — serious, specific, and cleanly fixable, which is exactly what happened.

Where to focus

Top production-readiness risks, prioritized

None of these are cosmetic, and none require rethinking the product. They're the operational safety net a fleet control-plane needs before "production-grade" is a fair label.

01

Zero automated tests & no CI

A regression in command authorization — the exact Critical the pen-test found — could ship undetected and turn a low-privilege account into a fleet-wide wipe. Nothing currently guards it.

CRITICAL
02

No database backups or point-in-time recovery

This is the system of record for a 900-device fleet. Today a volume loss or a bad migration has no documented recovery path.

CRITICAL
03

Single-instance architecture

The real-time hub lives entirely in one process's memory. There's no horizontal scaling and no zero-downtime deploy path — the control plane is a single point of failure for the whole fleet's live channel. Adequate at ~900 devices; a ceiling beyond.

HIGH
04

Static, shared, non-rotatable secrets

One fleet-wide device API key with the serial number as the only identity, plus a shared admin key. One leak compromises everything, and there's no per-device revocation or rotation mechanism — the weakest link in an otherwise strong trust model.

HIGH
05

Thin operational envelope

No graceful shutdown, no metrics/tracing/structured logging, no resource limits, no in-repo TLS or runbooks — production relies on undocumented external AWS infrastructure.

MEDIUM
06

Two concrete, fixable defects

A migration statement alters release_problems before the table is created — likely breaking a fresh-database install. And the agent's shell allowlist checks only the first token yet runs the whole string via sh -c, so it's bypassable. Both are small, targeted fixes.

MEDIUM
The plan

Path to production

A phased hardening plan. Nothing here is a rewrite — it's the discipline layer that turns a strong MVP into a system you can stake a business on.

Phase 1 · Must-do
Stop the bleeding
  • Automated tests around command authorization + a CI pipeline
  • Automated Postgres backups with point-in-time recovery
  • Fix the fresh-install migration bug & the shell-allowlist bypass
  • Add graceful shutdown & HTTP read/write timeouts
Phase 2 · Hardening
Trust & visibility
  • Per-device enrollment credentials with rotation/revocation
  • Step-up MFA on destructive commands
  • Metrics, tracing & structured logging; server healthchecks
  • Resource limits, run-as-non-root, documented TLS & runbooks
Phase 3 · Scale
Grow past one node
  • External pub/sub (Redis/NATS) to free the real-time hub for HA
  • Partition the high-volume check-ins table
  • Complete the alert matrix (Phase-2 device telemetry)
  • Prune demo scaffolding from served assets; break up the monolith files
The one-line takeaway for the room

AIO MDM already does the hard product things well — deep fleet control, real OTA with QA sign-off, live remote access, AI assistance, and a pen-tested security model with the serious findings fixed. What stands between it and "production-grade" is a well-scoped operational punch-list, not a redesign.
