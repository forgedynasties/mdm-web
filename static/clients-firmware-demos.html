Clients · folding the three firmware entries into one

The rail carries Firmware client · QCOM, · GMS and · userdebug as separate entries. They are one client — same package, same source, same version — split only because each is signed with a different platform key, and a device can only install the build signed with the key it already trusts. That split has to survive whatever we do here: it is what stopped a GMS device being handed the QCOM APK. The question is only whether it deserves three rail entries or one entry with the variants inside it. Three options below, each shown with the real data now on stage.

A · Three entries deployed now

One rail row per signing key. Good: nothing is ever ambiguous — the entry you open is the exact artifact that gets installed, and publishing is per-entry. Bad: three quarters of the rail is one client, the name is repeated three times, and "how many devices are behind on the firmware client" cannot be read anywhere — you have to open three pages and add up.

B · One entry, variant switcher would pick

One Firmware client row in the rail, carrying the whole firmware fleet. Inside, a segmented control picks the variant, and everything below it — cards, devices, releases, publish target — is that variant's. Good: the rail says what it is (one client, six devices), the variant is still an explicit choice you can see, and the page below is the page you already know. Bad: one more click to reach a specific tree, and the variant choice is not in the URL unless we put it there (we would: ?slot=firmware-qcom keeps working, so existing links and the publish API are untouched).

C · One entry, all variants at once

One rail row, no switcher. A Builds strip lists the variants as rows — hosted version, signing key, devices, behind — and under it a single device table for the whole firmware fleet with a Build column. Good: the state of every tree is on one screen; "which trees am I behind on" is one glance; updating a mixed set is one button. Bad: the busiest of the three, and the per-variant publish/download links have to live in the strip rows rather than at the bottom of the page. With more trees it grows.

What I would do

B. The rail stops repeating one client's name three times and finally answers "how big is the firmware fleet", while the variant stays a thing you pick on purpose — which matters, because picking wrong is the one mistake this page exists to prevent. C reads better on a day where several trees are behind at once, but that is the rarer day, and it puts the signing key in a table cell where a mis-scan is easy. Either way ?slot=firmware-qcom keeps working and the publish API does not change, so CI and the OTA console need no edits.
