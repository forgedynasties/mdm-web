C · Inventory to clean up

Part 2

"Collect logs"

A correction to the review first. It said the shell was used 1,223 times in 30 days, 986 of them to run logcat, and that "Collect logs" would replace the most common use of the shell. That was wrong. Looking at who ran them:
  • 919 had no person behind them: the server's own legacy-OTA watcher (internal/api/legacy_watch.go) polling logcat -d -s update_engine | tail -n 60. 913 of the 919 are that one command.
  • 141 came from an API key (scripts, including mine), 163 from the shared admin account.
  • Of the ~300 that people or scripts ran, the biggest groups were watching an OTA (87, update_engine) and reading thermal zones in a loop (~70, now covered by fast temperature). The rest are one-offs: getprop, du, setprop, bootctl.
  • No one ran bugreport or a general logcat dump. There are already 9 one-click diagnostics (Battery, Storage, Wi-Fi, "logcat update engine", …), run 37 times in 30 days.
So there is no demonstrated demand for a log bundle. It may still be worth having for crash investigations, but it isn't replacing anything.

L1 · A full "Collect logs" bundle

A device action and a bulk action. The device (firmware client only; MDM-Lite can't) runs a fixed set, and the result is one file per device to download, or a zip for a bulk run. Operators may run it; no shell needed.

L2 · More one-click diagnostics Recommended

Use what is already there: the device page's one-click diagnostics (Settings → Queries). Add presets for what people actually ran through the shell, make them available as a bulk action from the Devices list, and let operators run them. The result lands in the command history like today.

BatteryStorageWi-Filogcat update engine…5 more today + OTA progress+ Boot slot+ Build properties+ Recent errors (logcat *:E, 300 lines)

Bulk: select devices → "Run diagnostic" → pick one → results per device in the command history.

Good at
  • Covers what was really run: OTA progress, boot slot, getprop, a short error log.
  • Small: presets plus a bulk entry point and an operator permission. No new storage.
Bad at
  • Not a full log bundle; a long logcat still means the live log viewer.

L3 · Not now

Skip it and spend the time on the operating gaps next (rollouts that pause on failed installs, per-restaurant policies, two-factor login and scoped API keys). Revisit if people start asking for logs after crashes.

Recommendation

C1, the checklist card, and L2, more one-click diagnostics. C1 turns the one big fact about the fleet list (half of it is silent) into jobs with a place to do them, and keeps the 10 silent restaurant devices in view. For logs, the review's reason for a bundle turned out to be wrong, so L2 covers what was actually run through the shell for a fraction of the work. L1 can follow if crash investigations start asking for it.
