Scout enrolment — handover for the next agent

Feature "a T7 enrols the other devices in its restaurant": a firmware device (scout) sweeps its venue's Wi-Fi on :5555 with the fleet adb key, reports what answers, and on approval installs the standard (DPC) client on a stock device over adb and makes it Device Owner. Stage only. This file is the state as of 2026-10-08 (second session appended below) and exactly what is left to do. Design: plan (section 7 is the implemented design), inbox demos (the UI that shipped is option 1A).

Two caveats that decide whether the test finds anything

1. NetScout sweeps only 231's own /24. 231 is 10.32.3.29, so it scans 10.32.3.1-254 only (NetScout.subnetHosts). The earlier lab devices were on 10.32.1.x/10.32.2.x — a different /24 — so 231 will NOT see them. For a positive find, put a key-trusting device on 10.32.3.x: e.g. the feat/sunmi-mock T7 (image at ~/A15/QCOM6125_A15_T7_new branch feat/sunmi-mock: no MDM client, adb on 5555, our key in /adb_keys), or any device flashed to the vendor contract, joined to the same /24 as 231. mDNS discovery was in the plan but is NOT in the shipped Java (sweep + :5555 only); cross-subnet discovery is future work.
2. The stage fleet keypair must match the devices' /adb_keys. The scout authenticates with the private key stage holds (fingerprint 00025f10e96f). A target only opens if its /adb_keys holds the matching public key. If every target comes back "refused the key", the stage keypair is not the one baked into the images — upload the correct pair via PUT /api/v1/fleet-adb-key (the public half must equal the devices' adbkey.pub; see internal/fleetkey and the qcom tree's qssi/device/qcom/qssi/aio-adb_keys).

Design decisions already settled (do not re-litigate)

  • Key travels per scan/job inside the frame, held in memory only, never on disk, only ever to a firmware device. Audited server-side as fleet_adb_key.scout — actually logged as the device.enroll audit line "via <scout>".
  • Approve mints a one-shot enrollment profile (max_enrolls=1, 10 min, placed at the venue) via CreateEnrollmentProfile; the device enrols with it exactly like any DPC device, so the server confirms the enrolment itself.
  • Class guess reuses prod.ClassForModel; the approver can override in the Enrol row.
  • Blockers (account / foreign Device Owner / second user) mirror tools/enroll-adb.sh; blocked rows stay with a reason and a "Check again" (ScoutRecheck re-probes one host).
  • Phase 3 auto-enrol is intentionally NOT wired: the restaurants.auto_enroll column exists (default false) but the scheduler only scans + prunes. One-click approve is the ceiling until real scans have run.
