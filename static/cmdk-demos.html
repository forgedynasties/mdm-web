⌘K search: the new look

The palette got new behaviour today (on stage): one ranking across devices, venues and pages, Enter waits for the device search, and search covers IP and venue. The server now also sends each device's online state, venue and class. The list still looks the same and doesn't show any of that yet. Below are four ways it could look. Each mock has four states: open with nothing typed, a serial fragment, a word, and Enter pressed before the device search came back.

Already fixed, the same in every option (stage, commits ba4b7aa / f0c7add):
  • Enter while the device search is still running now waits for it and opens the top result. Before, it went to /devices/231 → "not found".
  • Venues and groups are filtered by the user's access scope. The device search filters by scope before its limit of 8, so a restricted user's own device can't be pushed out by hidden ones.
  • Devices, venues and pages are ranked together (exact → prefix → word → substring → fuzzy), so "front" puts the "Front counter" device first.
  • Devices also match by IP and venue name. A query that looks like a version (v2.1, 1.025) offers "Devices on build …".
  • The index is kept between opens and loaded ahead of time, so ⌘K never waits for it.

A · Current deployed

One line per row: the label, and an uppercase tag on the right. A device shows only "DEVICE", so you can't see whether it is online or where it is. With nothing typed it lists all ~28 pages in dock order.

Good
  • Compact, quiet, fast to scan for pages.
  • Nothing to learn.
Bad
  • Can't tell two similar serials apart, or an offline device from an online one, without opening it.
  • Empty state is a long list of pages you already have in the dock.

B · Grouped by kind

Section headers (Devices, Venues & groups, Pages, People) with two-line rows. Each device shows its venue, type and build, plus an online dot. The empty state shows recent devices and recent pages.

Good
  • Easy to scan when you know what kind of thing you want.
  • Rich device rows: dot, venue, type.
Bad
  • Works against the new ranking: the best hit can sit in the second group, below weaker matches in the first, and Enter still takes the top row.
  • Headers cost height, so fewer results fit.

C · One ranked list, rich rows my pick

The order follows the ranking exactly: whatever matched best is on top, whatever its kind. Every row has an icon for its kind, a two-line label (device: venue · type · build) and the online dot with how long it has been offline. The matched characters are highlighted, so you can see why a row matched (serial, IP, venue). The empty state shows recent devices and pages, then the full page list. A footer shows the keys.

Good
  • What you see is what Enter opens: row 1 is the top match.
  • Shows why a row matched (highlighted IP, venue named in line 2).
  • Fits the existing panel width, and no new styles outside the palette.
Bad
  • Two-line rows: about 7 results visible instead of 11.
  • With no headers, the kind shows only through the icon and a small label.

D · List + device preview

A wider panel. The ranked list is on the left; on the right, a preview of the highlighted device (status, battery, venue, build, last seen) with quick actions: Open, Screenshot, Reboot. Below 720px the preview is hidden and it behaves like C.

Good
  • Answers "is it up?" without leaving the page.
  • Room for actions later ("reboot 231").
Bad
  • The actions are new surface: each needs the access check, a confirm and the right per-device capabilities. That is a separate project.
  • A wide modal for what is mostly a jump bar; the preview is empty for pages.

My pick

C. The new behaviour is a single ranking, and C is the only layout that shows that ranking as it is. Row 1 is what Enter opens, which is the guarantee the "231 + Enter" fix depends on. B's groups would put back the mismatch between what you see and what Enter does. D's preview and actions are worth doing, but as a later step on top of C, since C's rows are already the left side of D. To build C: the row markup, the online dot and "offline 2 h" (needs last_seen in the search JSON, a one-line change), recent devices (the recents list already records /devices/… visits), match highlighting, and the footer.
