3 · Findings

F1 · Client updates read as "Install app" on the device page High

Where: device.html action timeline (92), device queue (133), Activity card (3262): {{if $c.ApkURL}}Install app{{else}}{{cmdLabel $c.Type}}{{end}}. Why: the override was written when only installs carried an APK; a client self-update now does too.

  • 32 client updates in 30 days are listed as installs on device pages. The device filter "Install" does not find them either.
  • The command detail page resolves the APK URL against the app library, so a client update can head itself with whatever library entry shares the URL.

F2 · "Update app" is the wrong name for a client update, and says nothing about the client High

Where: cmdTypeLabel("app_update"), cmdHint (no case → APK filename), the row verb (install_apk → "installed", everything else → "delivered").

  • Payload carries package, version, sha256. The row should read Client update · Firmware client 1.8.9 (or Standard client 0.2.9), with "updated" as the verb.
  • Shares one history with app installs, but the Clients page already owns client rollouts: a row here should link back to it.

F3 · Update reboots are recognised by author, not by what they are High

Where: isSystemReboot (c.Type == "reboot" && c.CreatedBy == ""), the "Update reboot" title in commands.html:2048, and no equivalent on the device page.

  • 27 of 97 update reboots were sent by a person ("Reboot to apply") and are listed as plain reboots; on the device page all 97 are plain reboots.
  • The reliable marker is the payload {"reason":"ota"}, which every one of them carries. Any reboot with that reason should be "Update reboot", clustered or not, and ideally link to the deployment.

F4 · The legacy OTA progress probe is 911 shell rows nobody sent High

Where: internal/api/legacy_watch.go › sendLegacyProbe creates a shell command with an empty author every tick while a legacy OTA is being watched.

  • Admins see them as "Shell" by nobody with no hint; failed ones are counted in Needs attention; they are three quarters of all shell rows and skew the per-person history on profiles.
  • They are an implementation detail of OTA progress, not an action. They should be excluded from every history list and from the attention count (a created_by = '' + reason marker, or a dedicated internal type), or sent outside the commands table.

F5 · Needs attention is counted but not shown on Actions High

Where: commands.html:270 headline vs cmd-timeline-inner (2000–2012), which has no .Attention group. The data is already in the template.

  • Render the group above In progress, with its "Clear" action, and make the headline number a link to /commands/history?status=attention.

F6 · Raw type keys leak: adb_tcp and friends Medium

Where: cmdTypeLabel default branch; cmdHint has no case for adb_tcp, ota, reboot, app_update, set_kiosk, wipe.

  • 50 "adb_tcp" rows this month. Should be Wireless adb · on for 4 h / Wireless adb · off. OTA rows should name the release; kiosk rows the rule.

F7 · Device page filters cover five of thirteen types Low

Where: device.html:81–86: All, Install, Uninstall, Shell, Screenshot, Reboot.

  • Client updates, OTA, wireless adb, queries and log collection are reachable only under All. Add pills for Client update, OTA, Wireless adb, Query/Logs, or build the pills from the types present.

F8 · Per-device OTA rows say "OTA Update" and nothing else Low

Where: cmdTypeLabel("ota"), no hint; the payload names the release.

  • Device page should read OTA · v2.1.025 and link to the deployment. Actions correctly leaves these to Updates.
