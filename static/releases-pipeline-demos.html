Releases: the pipeline, worked out

You picked the pipeline on the releases demos. That sketch had three gaps, and this page closes them. First, it had no fleet-wide view: the role tabs now carry each role's status, so a problem in another role shows without opening it. Second, firmware is per model, not per role. A role can mix our hardware with another company's: the self-order kiosk role has our Kiosk 18/22/27 on the Firmware client and the ZC-3568K on the Standard client. So the firmware lane has a chip per model, and each model has its own firmware switch in the Role table (below). The app lane stays per role, because every model in a role runs the role's one app. Third, the lab columns are the app's package variants (internal, uatv2), not numbered slots, so a new build goes to the column of its own package and only the move to prod asks for confirmation. Names, versions and counts are made up.

The Role table tab: where per-model lives

One row per hardware model. It holds the model-to-role mapping you asked for (many models per role) and the per-model firmware setting: Prod (deployed devices follow prod firmware), Lab only (builds go to lab devices; deployed devices keep what they have), or Off. An unknown model shows up here as "role needed" when it first enrolls. The client column is reported by the device, not set here.

What each move does

Columns are package variants. Prod is the base package (aio.app.nugget); internal and uatv2 are their own packages. A new build lands in the column of its package, so the only choice is when to release it. Lab devices on a variant pick it up in their own quiet window. Moving a device between variants installs the new package and removes the old one, so one package stays and nothing is ever downgraded in place.
Any → Prod. This needs the confirmation shown in the demo. Deployed devices pick it up in their quiet window, 20 per tick, and the previous prod build moves to "Earlier".
Firmware. Moves work the same way, one model at a time. A firmware build belongs to one model, matching the product key the OTA console already publishes with, so a Kiosk 22 build can never reach a Kiosk 27. Prod moves a device only within its own firmware line; a device on an older line is left alone and shown as such. Line changes, like the T7 v2.0 to v2.1 migration, are done as rollouts someone watches, not by the background job.

Later option for outside hardware. Android lets a Device Owner app install a maker's signed system update file. If the ZC-3568K's maker ships OTA files, the Standard client could install them, and that model's switch could then turn on. Not planned now. It needs the maker's files and a test on the device.

My recommendation

Chosen: B, the role list on the side. My earlier recommendation was A, because the role tabs answer the one weakness of the pipeline, the missing fleet view, without taking width from the lanes. The Library, Packages and Role table tabs keep today's firmware Packages page and lab-only APKs reachable, so the dock can merge Apps and Firmware into this one Releases entry.
