Command architecture — where it stands and where it should go

Written 9 Oct 2026, after AT070AABU00077 spent 15 hours checking in every five minutes, looking healthy on every page, with a queued shell command sitting at delivered that it never received and could never have received. The client bug behind it is fixed. This page is about the architecture that let a single dead thread take a device completely out of reach, and that gave nobody a way to see it.

Scope: the two clients in the lineup — the firmware client (com.aioapp.mdm, agent_kind = firmware, our AOSP images) and the DPC agent (aio.app.mdmclient.dpc, agent_type = dpc, off-the-shelf hardware). MDM-lite is gone from the active set; where the server still has a lite branch in this path it is vestigial and is called out as such. Both live clients take commands over the WebSocket and only over the WebSocket, so both have the failure below — they differ in how well they recover from it.

The claim of this page: there is nothing wrong with the command model — one queue, strict per-device FIFO, explicit acks, redrive sweeps. What is wrong is that delivery is push-only. Everything downstream of that assumption inherits it: presence means "has a socket", "delivered" means "written to a socket", and a device that cannot be pushed to simply has no path at all.

Four of the five require a socket. The fifth is new, rides a five-minute telemetry schedule, and is a backup, not a channel.

Eligibility — one good query

GetPendingCommandsForDevice is the only place that decides what a device may run, and it is the strongest part of the system:

  • A one-hour delivery window, so a day-old queued reboot never fires on reconnect.
  • Terminal states excluded; delivered re-delivers unless received_at is set, because writing to a half-open socket is not delivery.
  • Strict per-device FIFO, one command in flight at a time — OTA exempt in both directions.
  • Reboot exempt from re-delivery; it completes on the next boot via CompleteDeliveredReboots.

Keep all of this. The redesign below changes how a command gets to the device, not which command is next.

The split is the point. Fourteen queued action types are the entire remote control surface of the fleet, including the one that ships fixes (app_update) and the one people fall back on when a device is unreachable (adb_tcp). All fourteen currently depend on a socket.

Who issues them

Not only operators, which is why silent delivery failure compounds: the dashboard and API create commands by hand, and the server creates them on its own for scheduled reboots, the post-OTA reboot, redrive-stuck-reboots, scheduled recipes, and the adb_tcp a tunnel needs. A server-issued command that never lands has nobody watching for its output at all — it just quietly does not happen.

Return path — already transport-agnostic

Results do not have this problem, in either client. POST /api/v1/commands/{id}/ack takes received, the interim states, and the terminal ones; /logcat, /ota/status and /ota/progress are HTTP too. The firmware client persists unsent acks and drains them later; the DPC agent's Acker picks HTTP whenever the socket is down. Commands already come back over HTTP — they just cannot go out that way. That asymmetry is the whole bug class.

Two queues, not one

commands is the queue everything above describes. logcat_requests is a second queue with its own table, its own flush (flushPendingLogcatRequests), no redrive, no expiry and no HTTP path at all. Live control frames — remote screen, adb tunnel, telemetry_request, checkin_now, wake_screen, ping — are not queued anywhere; they are fire-and-forget WS frames, which is correct for a live session and wrong for anything that should survive a reconnect.

2 · What is actually wrong

The same fault, twice. Nothing above prevents the socket thread from dying — the client fix does that. This is about what the fault costs when it happens anyway: fifteen hours and a site visit, or a minute of latency and an alert.

1. Delivery assumes a socket, and nothing notices when there isn't one.

A device with no socket is unreachable, indefinitely, with no alert, no counter and a dashboard that calls it Offline next to "last seen: just now". The failure is silent by construction, which is why it cost a day. alert + gauge landed

2. "delivered" is not delivery.

It means hub.Push enqueued a frame. The eligibility query knows this and ignores delivered without received_at — but the dashboard shows the operator a delivery tick, and the operator believes it. The status the UI trusts is not the status the system trusts.

3. The server decides when a device gets work.

Every path is server-initiated, so every path needs the server to hold a working connection to that device. Neither client can ask for work — the firmware client could not until 1.9.5, and the DPC agent still cannot. Inverting this is the fix: the device is the only party that always knows whether it can be reached, and both clients already know how to talk HTTP for everything else.

4. Three notions of presence, none of them "controllable".

hub.IsConnectedForDisplay (socket + 30s grace), MarkCheckinPresence (mdm-lite only), and last_seen_at. None answers the one question an operator has before pressing a button: will this run?

5. Logcat requests cannot reach a socket-less device at all.

Second queue, second lifecycle, half the machinery. Diagnostics are exactly what you want from a device that is misbehaving, and they are the one thing with no fallback.

6. Nothing records a successful round trip.

There is no per-device "last command that actually completed", so "we think it is manageable" is never tested until someone needs it to work.

7. The UI promises things the transport cannot do.

A dashboard Shell command against a socket-less device waits five minutes and reports "Timed out — no output". It could have said, before sending, that this device holds no socket and the command will be picked up on its next poll.

3 · The proposal: one queue, device-pulled, socket as an accelerator

Principle. The device fetches its own work. The WebSocket stops carrying commands and carries one thing instead: "there is work, come and get it." A socket makes delivery instant; no socket makes it a minute late. Nothing makes it impossible.

Proposed. The arrow that matters now points left: the device asks. The socket makes that instant instead of making it possible, so losing it costs latency rather than control.

create command ──▶ queue (commands table, eligibility unchanged) │ ├─ socket up ──▶ WS: {"type":"wake"} ──▶ device GETs /commands/pending (instant) │ └─ no socket ──▶ device GETs /commands/pending every 60s (≤1 min) device ──▶ POST /commands/{id}/ack received → running → terminal (unchanged, already HTTP)

The one delivery endpoint

GET /api/v1/commands/pending?serial=AT070AABU00077     (device key, same auth as /ws)
→ 200 {"commands":[{"id":"…","command_type":"shell","apk_url":"","payload":{…}}]}

  · Returns what GetPendingCommandsForDevice already returns — same window, same FIFO,
    same one-at-a-time gate. No second opinion about what is next.
  · Marks 'delivered' (now meaning "handed to the device", which over HTTP it is).
  · Cheap and bounded: one indexed query, empty for almost every call.

Every existing push path then becomes the same two lines — wake the device if it is connected — and marshalCommand, the flush-on-connect loop, the stuck-delivery re-push and the unflushed sweep collapse into it. A half-open socket can no longer false-deliver, because a lost wake frame costs at most one poll interval instead of a command.

Client: a command loop that is not the telemetry loop

  • Poll on its own 60s cadence while there is no usable socket; stop polling when the socket is healthy (the wake frame covers that case).
  • Poll immediately on a wake frame, and once more after each terminal ack, so a queue drains at socket speed rather than one command per minute.
  • Telemetry keeps its own five-minute keyframe schedule, untouched. Command latency and telemetry volume are separate problems and must not share a dial — minutely check-ins would multiply the fleet's telemetry writes by five to fix a delivery bug.
  • Everything after fetch is the code that already runs for a pushed command: handleIncomingCommand acks receipt, dedupes by id against in-flight and persisted recently-done sets, and runs on heavyExecutor.

Both sides get simpler. The server's question shrinks to "can I hurry this along?", and the device owns the one question only it can answer: "can I be reached right now?"

On battery, Doze floors allow-while-idle alarms near five minutes, so a true 60s cadence is real on mains-powered kiosks and docked tablets, and best-effort on a tablet asleep in a drawer. That is the right trade: a device in a drawer is not one someone is waiting on.

Status vocabulary, made honest

StateMeansChange

The states already exist. What is missing is that the dashboard ticks at sent, while the eligibility query — correctly — only trusts received.

One line of UI work pays for itself: an operator who can tell "we sent it" from "it has it" would have diagnosed 00077 in a minute.

Controllability as a stored fact

One field, computed on check-in and on connect: ws (socket, instant), http (no socket, polls — reachable, delayed), none (no socket and a client that cannot poll: every firmware build before 1.9.5, which includes all 101 v2.0.x devices, and every DPC build before the one that adds the poll). It drives the device-page banner, the no_command_channel alert, the devices_no_command_channel gauge, and a pre-flight note on the Shell box instead of a five-minute timeout.

Fold the second queue in

A logcat request becomes a command of type logcat — one queue, one lifecycle, one delivery endpoint, and diagnostics that work on exactly the devices that need diagnosing. Live frames (remote screen, adb tunnel, wake screen, telemetry_request) stay WS-only and are documented as live-only, with the UI saying so up front rather than failing late.

Prove it, per device

devices.last_command_ok_at, stamped on every terminal ack. "Reporting for a week, nothing completed in a week" is a question worth asking automatically, and today nothing can ask it.

4 · Unlearning it — the textbook design

Everything above is incremental: it takes today's model as given and fixes its worst assumption. This section does the opposite — it forgets the current code and asks what a device control plane should look like. It is the yardstick, not the plan; §5 says how much of it is worth actually building.

Four layers, one direction of dependency. Nothing above the channel knows whether a device holds a socket; nothing below it knows who asked.

The eight ideas that matter

1 · Separate desired state from operations. Most of what this MDM calls a "command" is not an operation at all — it is a statement about how a device should be: in kiosk on this package, with these apps, on this build, with this config. Those belong in a desired-state document the device reconciles against continuously. A reconciler needs no delivery guarantee, no retry logic and no queue: a device that misses an update converges on its next loop, and a device that is reflashed converges from scratch. Only genuinely one-shot acts — reboot now, wipe, run this shell line, take a screenshot — are jobs. Roughly half of today's command types would stop being commands.

2 · Pull is the contract; push is a hint. One interface: Fetch (give me my work) and Hint (there is work, fetch sooner). The socket implements the hint and nothing else. This is the single decision that makes the whole class of failure impossible rather than detected — and it is why the incremental plan in §3 is pointed the same way.

3 · Leases, not "delivered". A job is handed out as a lease: lease_id, an expiry, and a heartbeat the device extends while it works. Expiry returns the job to the queue automatically. No sweeps, no 90-second staleness constant, no re-push logic, no "delivered means we wrote it to a socket" — the ambiguity that made 00077 confusing cannot be expressed in this model.

4 · Declare the guarantee per type, don't imply it. Three classes, named in a registry beside each type: at-most-once (wipe, reboot — a double-run is worse than a miss), at-least-once + idempotent (install an app, apply config — retry freely, the device dedups by idempotency key), best-effort live (remote control, tunnels — no queue, and the UI says so). Today these rules exist, but spread across a SQL CASE, a break in a loop, and two sweep jobs.

5 · Append-only events instead of a mutated status column. One row per thing that happened, never updated. Current status is a projection. "When did the device actually get it" stops being guesswork, the audit trail is free, and the UI can show sent and received as the different facts they are without anyone having to remember that one is a lie.

6 · Serialization keys, not one queue per device. Strict per-device FIFO is too coarse: a wedged install should not stop a screenshot or a reboot. Each job names a concurrency group (install, firmware, shell) and only shares a lane with its own kind. Today's design reaches for the same safety with a global per-device gate plus an OTA exemption carved out of it — which is the right instinct expressed once, by hand.

7 · Capability negotiation, enforced at enqueue. The device declares what it supports; the server refuses to create a job the device cannot run and the UI never offers it. The pieces exist (product/caps.go, otagate, capabilities_degraded) but are advisory — a DPC agent still has to answer unsupported to a boot-splash command that should never have been created.

8 · Controllability is an SLO, measured by a canary. Not "is the socket up" but "did a round trip complete recently". A cheap synthetic no-op job per device per day, plus last_round_trip_ok_at, turns "we believe the fleet is manageable" into a number that can page someone. Today nothing anywhere tests it, which is precisely why a 15-hour outage was invisible.

What I would actually build, and what I would not

Worth it: ideas 2, 3 and 8 — pull-as-contract, leases, and a round-trip canary. They are small, they compose with the existing queue, and together they close this failure class permanently. Idea 5's visible half (showing received rather than sent) is an afternoon and removes the thing that misled us.

Worth it later: idea 6 (concurrency groups) the next time a wedged install blocks a queue, and idea 4 (a type registry) as the natural home for rules that are currently scattered.

Not worth rebuilding now: idea 1. Moving config, app sets and kiosk policy to a full reconciler is the most architecturally correct item here and the largest rewrite on the page — it touches every client, the config push path, the deployments model and the dashboard. The honest position: the firmware client's config already arrives declaratively in the check-in response and is applied idempotently, so the most valuable part of idea 1 is already true where it matters. Full event sourcing (idea 5's storage half) likewise buys audit quality we are not currently short of.

Put bluntly: the textbook design and the plan in §3 differ by two features (leases, concurrency groups) and one rewrite we should not do. That is a reassuring result — it means the incremental path is not a compromise with the right answer, it is a prefix of it.

6 · Implementing §4 — the buildable version

Six of the eight textbook ideas are additive: new columns beside the existing commands / command_status tables, one new endpoint, one new Go package. No migration of live rows, no client left behind — a device that knows nothing about any of it keeps working over the WS push path exactly as it does today. That matters because 101 firmware devices will never get a new client.

Schema — all additive

The type registry — idea 4, and the home for scattered rules

One new package, internal/command, holding what is currently spread across shortLivedCommandsSQL, the break after a reboot, the OTA exemptions in GetPendingCommandsForDevice, and two sweep jobs:

type Spec struct {
    Type      string
    Guarantee Guarantee     // AtMostOnce | AtLeastOnce | BestEffortLive
    Lane      string        // concurrency group: "install", "firmware", "shell", "default"
    Deadline  time.Duration // per type, not per query
    Lease     time.Duration // how long a device may hold it before it returns to the queue
    NeedsCaps []string      // refused at enqueue if the device lacks them
    LiveOnly  bool          // never queued; the UI must say so up front
}

// reboot: AtMostOnce, lane "device", deadline 0 (completes on next boot), no re-delivery
// install_apk: AtLeastOnce, lane "install", lease 30m, heartbeat-extended
// shell: AtLeastOnce, lane "shell", deadline 5m
// ota: AtLeastOnce, lane "firmware", lease 2h, exempt from the device lane
// update_splash: NeedsCaps ["system_partition"] — refused at enqueue for DPC, not answered
//                "unsupported" after the fact

Enqueue consults it, so the dashboard stops offering a device actions it cannot run, and the eligibility query reads policy from columns the registry filled instead of re-deciding it.

Leases — idea 3, and the deletion of three sweep jobs

The pending query gains one clause and loses the rest of its delivery bookkeeping:

AND (cs.lease_expires_at IS NULL OR cs.lease_expires_at < NOW())   -- nobody holds it now
AND (cs.attempts < c.max_attempts)                                 -- give up honestly

Handing a job out sets lease_id, lease_expires_at = NOW() + spec.Lease and attempts = attempts + 1. A device holding a lease heartbeats it — the interim downloading / installing acks both clients already send are the heartbeat, so long installs need no new client code. An expired lease returns the job to the queue with no sweep at all, which retires redrive-stuck-deliveries, redrive-unflushed and the 90-second staleness constant, and makes expire-stalled-installs a thin wrapper over max_attempts.

Events — idea 5, written from day one, projected later

Every state transition also appends to command_events. Nothing reads it at first; command_status stays the live column so no page changes. Once the log exists the device page can show a real timeline ("queued 14:02 · leased 14:02 · received 14:03 · finished 14:04"), and the UI can finally distinguish sent from received — idea 5's visible half, which is the bit that would have saved the day we lost.

The canary — idea 8, the smallest item with the largest payoff

A daily job enqueues a no-op query per enrolled device, lane shell, deadline an hour. Its terminal ack stamps last_round_trip_ok_at. Then a device that has not completed a round trip in, say, 48 hours while still reporting raises control_stale — and the fleet gauge becomes "devices we have actually proven we can command", not "devices with a socket". Half a day of work, and it is the only item here that would have caught 00077 without anybody suspecting anything.

Idea 1, scoped honestly

A full desired-state reconciler is the one thing on this page I would not build now. It touches both clients, the config push path, the deployments model and most of the dashboard, and its most valuable third is already true: the firmware client's config arrives declaratively in the check-in response and is applied idempotently every time. The cheap slice worth taking is the reported half — have each client report the state it believes it is in (kiosk on/off, package, app set hash, build) and show drift against desired on the device page. That is a day, needs no new plane, and answers "did that config actually take?", which today nobody can answer either.

Does the WebSocket stop carrying command payloads (step 5)?

Yes is the simplification that deletes three code paths and makes a half-open socket harmless. No keeps instant delivery on a path that is proven in production and leaves the poll as a pure fallback — less elegant, less risk to the thing that works today for 50 connected devices.

Poll interval, and does it back off?

60s flat is simplest. 60s for the first ten minutes then 5 min would cut the request volume of a fleet where a few devices sit socket-less for days — at the cost of a device being up to five minutes from reach when someone finally needs it.

Do socket-less devices poll at all when nothing is queued?

They must — otherwise there is no channel to be surprised by. The query is cheap and returns empty. 188 devices at 60s is ~3 requests a second.

One release for both clients, or firmware first?

The DPC agent is the easier port and the safer place to prove it (4 lab devices, silent self-update, nothing in a restaurant yet). Firmware first reaches the fleet that actually suffered the bug, but only its v2.1.x half. Doing DPC first and firmware second costs a week and de-risks the fleet roll.

Fold logcat into commands now or later?

It is the clean end state, and it is also a migration of a live table with its own UI. Later, unless diagnostics on socket-less devices is itself urgent.
