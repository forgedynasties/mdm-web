MDM firmware client · GTS certification · T7

GTS Device Owner Fix

Every T7 was un-certifiable, because the MDM client made itself the device’s Device Owner and an active admin on every boot — registrations only the app itself may remove. One client change removes them: no Device Owner, and an admin only while a device is in kiosk mode.

Brief summary

The firmware client claimed Device Owner + active admin at every service start — so, every boot — and Google’s GTS harness cannot take either away from a non-test-only app. That broke three things: the device-policy tests (10 failures), whole module parameterizations (device-owner removal aborts the module), and multiuser tests (a provisioned owner leaves the no_add_user restriction set).

Kiosk mode never needed Device Owner either — lock task is authorised by the package allowlist the admin writes. So the client now never claims Device Owner, claims the admin only while kiosk mode is applied, releases it when kiosk mode goes off, and hands back any ownership it finds on startup — so field units clean themselves with no wipe. Verified on the T7: two of the three groups now pass outright; the third is structurally impossible but its ten 14_r2 methods are absent from the 13_r2 suite, so they could not be re-executed here.

03Root cause

Claimed on every boot, and only the app could give it back

// MdmService.java:285 — called from onCreate(), so on every service start
ensureDeviceOwner();

// MdmService.java:501-519
dpm.setActiveAdmin(adminComponent, true);
dpm.setDeviceOwner(adminComponent, android.os.UserHandle.USER_SYSTEM);

BootReceiver starts that service on BOOT_COMPLETED / LOCKED_BOOT_COMPLETED. The admin component has no android:testOnly, and res/xml/device_admin.xml is an empty <uses-policies /> — the app requested no admin policies at all; it only needed to be an admin.

The two APIs that can clear it are self-only by design: clearDeviceOwner() requires the caller to be the owner package, and removeActiveAdmin() is allowed for the component’s owning package (and silently refuses while it is still the owner). That constraint is why this had to be a client fix.

04Key finding

Kiosk never needed Device Owner

The client’s only use of DevicePolicyManager is entering kiosk mode (lock task), and three citations from this tree’s framework show ownership was incidental:

  • Lock task is authorised by the package allowlist. LockTaskController.getLockTaskAuth() → LOCK_TASK_AUTH_ALLOWLISTED when the package is in the list written by setLockTaskPackages; and startLockTaskMode(task, isSystemCaller=false, …) picks LOCK_TASK_MODE_LOCKED (nav bar hidden). Only startSystemLockTaskMode() — the screen-pinning entry — is pinned, matching the client’s own earlier finding.
  • The policy calls need an active admin, not an owner. enforceCanCallLockTaskLocked() requires MANAGE_DEVICE_POLICY_LOCK_TASK or an active admin owned by the caller; both setLockTaskPackages and setLockTaskFeatures go through it.
  • An admin can be claimed at any age; an owner cannot. setActiveAdmin() checks only MANAGE_DEVICE_ADMINS + cross-user. setDeviceOwner() is refused once USER_SETUP_COMPLETE is set (STATUS_USER_SETUP_COMPLETED) — which also rules out “claim ownership only when the server puts the device into kiosk mode”.

And clearing the owner clears the restrictions the framework attached to it (clearDeviceOwnerLocked() → clearDeviceOwnerUserRestriction()) — including DISALLOW_ADD_USER. That is why group C failed for free.

05The fix

How it was fixed

Four moves in the client, all of them in the app because Android only lets the owning package release these registrations:

  1. Stop claiming Device Owner. The setDeviceOwner call is gone — the app never takes the role again. (Four lines deleted, one call added in its place.)
  2. Claim the admin on demand. The admin is registered inside KioskManager.apply(), immediately before the lock-task policy is written — so it exists only while kiosk mode is actually being applied.
  3. Give the admin back when kiosk mode goes off. Clear the allowlist, stop lock task, then unregister the admin: the device returns to the state a GTS run needs without anyone touching it.
  4. Self-heal on startup. releaseDeviceOwnerIfAny() clears ownership if the app holds it; releaseAdminIfUnused() returns the admin when no kiosk-mode config exists. Units already in the field therefore clean themselves on their next boot — no wipe, no visit, no operator command.
// before — MdmService, on every service start (i.e. every boot)
dpm.setActiveAdmin(adminComponent, true);
dpm.setDeviceOwner(adminComponent, UserHandle.USER_SYSTEM);   // owned the device, permanently

// after — MdmService, on every service start
if (dpm.isDeviceOwnerApp(getPackageName())) dpm.clearDeviceOwnerApp(getPackageName());
KioskManager.releaseAdminIfUnused(this, dpm, adminComponent);  // kiosk mode off -> hand it back

// and — KioskManager.apply(), only when kiosk mode is being applied
ensureAdmin(dpm, admin);                                       // claim it here, on demand
dpm.setLockTaskPackages(admin, new String[]{pkg, ctx.getPackageName()});

The invariant that falls out of those four moves: an active admin exists on this device if and only if kiosk mode is enabled for it. Kiosk mode still works because lock task needs the package allowlist and an active admin to write it — not ownership.

07Still open

What this does not close

  • The image still ships the old client. The fix reached the test unit as an APK self-update; the AOSP tree’s submodule pointer still pins c2e72d3 (1.0.4). A factory reset wipes /data, so the first boot would re-claim Device Owner. Before a certification run: push the client repo (done — 5e8ba9f), bump qssi/packages/apps/mdm-client, rebuild qssi, flash.
  • Kiosk mode on the new client is untested. The release path is proven end-to-end; the claim path (admin claimed when kiosk mode is enabled → LOCK_TASK_MODE_LOCKED) rests on the framework citations, not a run. One kiosk-mode toggle on a lab unit closes it.
  • The ten 14_r2 tests are indirect only — 13_r2’s module lacks those five methods. Re-running them needs the 14_r2 suite.
  • The rest of the GTS failures are not MDM and remain: EDI / unrecognized service account (133 tests — needs APE_API_KEY and an initial EDI report via gts run gts --module GtsEdiHostTestCases), device network/DNS (33), vendor SELinux exemptions for qlog/qlog_app/dumpstate (5 × 2), ro.board.first_api_level=33 (2), GMS D2d backup-transport whitelist (2), GmsCore update owner (2).
  • Vendor-image question: the flagged qlog SELinux policy is not compiled by a build from the current tree state, and the D2d whitelist entry is present in /product/etc/sysconfig/google.xml on the built images — so parts of the archived report may come from a different vendor image. Worth confirming which image was tested before chasing those four causes.
