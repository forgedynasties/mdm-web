Linking release issues from the Releases page

Release issues are crashes that hit the same build on 3 or more devices in 14 days. Today they are listed only on the Alerts page. Below are three ways to reach them from Releases. The figures are live data from 30 Sep (fleet of 181 devices). Also fixed in the same change: one crash can have several wordings (permissioncontroller has four "safety source" variants), so issues are now grouped on the text up to the first comma. That turns v2.0.96l's four rows into one crash on 34 devices.

Current Deployed

No link. The crash counts for a build exist at /releases/{id}/crashes, but nothing on the list points there, and the list says nothing about crashes.

A · A tag on the release it belongs to Recommended

A red tag beside the status on each release with an issue: the number of issues and the widest reach. It links to that release's crash page. A tooltip names the apps.

Good at
  • The issue sits on the build that caused it, and whoever is deciding whether to push or pull a release sees it right there.
  • No new block on the page; rows with no issue don't change.
Bad at
  • An old build lower down the list (v2.0.96l here) is only seen by scrolling.
  • There's no fleet-wide count on the page.

B · A card above the list

A "Release issues" card between the KPIs and the list, one line per issue, each linking to its release's crashes, plus "All on Alerts". It is hidden when there are none.

Good at

  • It's a number with no build attached, and it takes you off the page to find out which release.

Recommendation

A · the tag on the release. The question on the Releases page is "is this build OK?", and A answers it on the build itself, one click from its crash list, without adding a block people scroll past. The fleet-wide list already lives on Alerts. If you also want the count at the top, C can be added to A later at no cost.
