AIO MDM · firmware client · September 2026

Command communication audit

What the firmware client and the server actually say to each other, where that breaks down, and what was changed. Every finding below was read out of the source on both sides — the not a gap section matters as much as the rest, because three things that look like gaps are working as designed.

01The path a command takes

Four transports. Only one of them carries commands to a modern firmware device, and that is deliberate.

TransportCarriesCadenceCommands?
GET /api/v1/wsdelta telemetry up, commands downlive Yes — the only path for firmware
POST /api/v1/checkinfull snapshot up~5 min Only legacy firmware and MDM-lite
POST /api/v1/commands/{id}/ackreceipt + terminal resulton eventdevice → server
otautil:8000legacy OTA polling15 minpre-agent builds only
The check-in response does carry a commands[] array, but it is filled only when LegacyCheckin() || isMDMLitePayload() and the device holds no socket. The modern firmware client is excluded from both branches, so it never receives commands that way — and it correctly never reads them.

02Gaps found and closed

The client never told the server it could take an MDM OTAfixed

The server reads extra.ota_supported and prefers that over guessing, and falls back to g.Build(buildID, productKey) — string-matching build-id lines — when it is absent. It was always absent: the firmware client emitted no ota_supported key. So the device-authoritative path existed and never once ran.

Now reported from ro.build.ab_update, which is the honest precondition: the OTA path hands the package to UpdateEngine, and that only exists on a seamless-update device.

A reported capability list replaced the defaults outrightfleet-wide riskfixed

CapSet() returned an advertised list instead of the product defaults. One capability missing from a client's list — a bug, or a build older than the capability — would silently withdraw that command from every firmware device at once, and the first symptom would be a button that stopped working on a rollout.

Firmware now merges: defaults first, advertised capabilities on top, so a report can only ever add. Stock devices keep the replacing behaviour — they have no defaults to merge with, and the DPC agent lists what it can do precisely because the server cannot know.

Cost, accepted deliberately: a firmware build can no longer use reporting to drop a capability it genuinely lacks. That belongs in DefaultCaps, keyed by product or build line, where it is reviewable.

Three command types that nothing could ever sendremoved

managed_config and wlc_set sat in commandNeeds with no creator anywhere in the server — their capabilities (config, wlc) gate nothing. ping, checkin_now and get_app_inventory held 5-minute expiry deadlines for command rows that were never created (checkin_now today is a bare WS frame, not a command).

The client still handled get_app_inventory — an orphan in both directions. Its inventory now rides every check-in as installed_apps, so the handler is gone too.

03Investigated, and not a gap

Recorded so nobody re-opens them. Each of these looked like a hole and is working as designed.

The receipt ack already exists — both halvesno change

The server's own comment names the gap: "the durable fix is a client receipt-ack so 'delivered' means the device has it rather than we enqueued it." That fix shipped. MarkCommandReceived, the received status on both the WS and HTTP ack paths, and received_at IS NULL in the redrive sweep are all present — and the client sends it first thing in handleIncomingCommand, even for duplicates, before the idempotency check. The 90-second redrive sweep is a backstop, not the mechanism.

Firmware gets no commands on the check-in responseno change

Not a missing feature: the server gates that array to legacy firmware and MDM-lite, and only when the device holds no socket. The modern client is deliberately excluded. A device that cannot hold a WebSocket is not silently queued for — it is a real availability question, but it is a design decision, not an oversight.

An unknown command type fails cleanlyno change

The dispatcher's default acks failed: "unknown type: X" rather than dropping the frame. An older client handed a newer command reports why instead of leaving the server waiting for a terminal state.

04Still open

Three allowlists that must agree, and nothing makes themopen

The dashboard (commandRoles), the admin API (validTypes) and the access policy catalogue (accessActions) each decide separately what may be sent. Verified divergence: the dashboard can send query and logcat; the admin API rejects both as invalid type. Defensible scoping — but undocumented, and a fourth type added to one list will not appear in the others.

mic_gain_set is built and blocked at the same timedecision

The client handles it, the server has a payload builder and merges its output into telemetry, and the only thing stopping it is the role allowlist — whose comment reads "mic gain is read-only from the MDM". Kept blocked. The entry and the branches stay so that enabling it remains a one-line change rather than a re-implementation.

The ack vocabulary is install-shapedopen

downloading | installing | installed | failed | completed describes an install. For shell, reboot, screenshot and update_splash everything collapses to completed/failed, and progress means nothing. The server cannot distinguish acknowledged from done for those types. Low harm, but it caps what the UI can honestly show.
