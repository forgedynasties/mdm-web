AIO MDM · firmware client

Audit and progress

We looked at how the server and the tablet client talk to each other, fixed what was broken, and tested the fix on a real tablet on stage. This page is the whole story in plain words.

What we foundThe client never told the server it can take an OTA update. So the server was guessing.
What we fixedThree things. The client now tells the server. Plus two risky bits of the server were made safe.
What we provedA real tablet on stage updated itself from 1.1.0 to 1.1.1 and started reporting the new field.

01How a command gets to a device

The tablet holds an open connection to the server. Commands come down that connection, and the tablet answers back to say "got it" and later "done" or "failed". There is a second, slower path where the tablet checks in every 5 minutes — but that path is only used by old firmware and by the MDM-lite agent, not by the current tablet client. That is on purpose, not a mistake.

02Problems we found, and what we did

The client never said it could take an OTA updatefixed

The server has a field it reads to find out whether a device can receive an over-the-air update. If the device doesn't send it, the server falls back to looking at the build name and guessing. The client never sent it. So the careful path existed and was never used — the server was guessing every time.

The client now sends it, worked out from a real property on the device rather than hardcoded.

Why it matters: guessing from a build name gets it wrong the day a build name doesn't follow the pattern, and then a device gets offered an update it can't install.

A device could have taken features away from the whole fleetriskyfixed

When a device tells the server what it can do, the server replaced its own assumptions with that list. That sounds fine until you think about what one missing entry does: if a client forgot to mention one thing it can do, every tablet in the fleet would quietly lose that button at the same time. Nobody would know why.

Now the device's list adds to what the server already knows. It can't take anything away, so a mistake in a client build can't disable a feature across the fleet. Stock Android devices keep the old behaviour, because for them there is nothing to add to — their list is all we know.

There is a test for this (`capset_test.go`) that checks both directions, because it is the change with the widest reach.

Three command types nothing could ever sendcleaned up

Three commands sat in the server's list with no code anywhere that could send them, and two of them also held a 5-minute deadline for commands that were never created. Dead entries like this are worse than useless — they look like working features and make the list harder to trust.

Removed. The client also still had a handler for one of them, so that went too.

03Things that looked like problems, but aren't

Worth writing down so nobody spends time on them again. I started to fix two of these before checking.

Commands don't come through the check-in pathby design

This looks like a hole — the server's check-in reply has a list of commands in it, and the client ignores it. But the server only fills that list for old firmware and MDM-lite, and only when the device isn't already connected. The current client is left out on purpose.

The "got it" reply already existedalready done

A comment in the server code asks for a fix that had already shipped. The client sends its "got it" reply the moment a command arrives — even for a duplicate — and the server uses it to stop re-sending. Nothing to do.

An unknown command fails honestlyalready done

If an older tablet is sent a command it doesn't recognise, it replies "failed: unknown type" instead of going quiet. The server always knows where it stands.

04What we shipped, in order

  1. Changed the client — it now reports whether it can take an OTA update, and the leftover handler for the removed command is gone.
  2. Changed the server — device capabilities now add to the defaults instead of replacing them, dead command types removed, and a test added for the capability rule.
  3. Bumped the client version to 1.1.1 (build 39). This matters: the server only offers an update when the new version number is higher, so publishing without a bump does nothing at all.
  4. Built and published to stage.
  5. Updated a real tablet (serial ending 0022) from stage and watched it happen.
  6. Tested it — see the result below.

06Trouble we hit along the way

Both are now handled automatically, so they can't bite the next person.

The build used a different copy of the code than we editedhandled

The firmware is built inside a big source tree, and that tree keeps its own copy of the client — not a link to the repo. So the first build after our change "succeeded" and produced the old app. It only showed up because the file size came out identical, which it shouldn't have.

The publish script now copies the repo's code into the tree before building, and says which it did.

The release notes described the wrong versionhandled

Release notes are taken from the last commit message. Our work wasn't committed, so the notes for 1.1.1 read like the 1.1.0 notes. You can now write them yourself, and 1.1.1's were corrected.

07Still open — nothing urgent

Three separate lists decide what may be sent, and nothing keeps them in stepopen

The dashboard, the admin API and the permissions system each keep their own list. Right now the dashboard can send two things the admin API refuses. That's a reasonable choice, but it isn't written down anywhere, and the next new command added to one list won't appear in the others.

One command is fully built but switched offdecision

Setting microphone gain works end to end, but the permissions list refuses it, with a note saying gain is read-only from the MDM. Left switched off. Everything is still in place, so turning it on is a one-line change rather than a rebuild.

The reply wording is built for app installsopen

Devices can say "downloading", "installing", "done" or "failed" — all install words. For a reboot or a screenshot everything collapses into "done", with no way to show progress. Not harmful, but it limits what the screens can honestly display.
