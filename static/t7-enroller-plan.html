A T7 enrols the other devices in its restaurant

Plan for zero-touch enrolment of off-the-shelf hardware (Sunmi, HK1 boxes, kiosk boards) by the T7 that is already on the venue's Wi-Fi. UI options are in t7-enroller-demos.html; option B (inbox) was picked on 8 Oct — its detail is section 7 and t7-enroller-inbox-demos.html. Nothing here is built yet.

1. Where we are

  • Our images trust our adb key. Since 5 Oct (6d3b2286ef9) the qcom tree ships /adb_keys with the fleet public key; adbd lets that key in with no prompt on every build variant.
  • The vendor contract exists as an image: branch feat/sunmi-mock (ef25778322d): no MDM client, persist.sys.usb.config=adb, persist.adb.tcp.port=5555, ro.adb.secure=1, our key in /adb_keys. That is exactly what we ask Sunmi and the others to put in their firmware for us. The T7 at 10.32.2.75 (AT070AA2600030) runs it and stands in for "a vendor device".
  • The server already holds the fleet key sealed under FLEET_ADB_KEY_SECRET (internal/fleetkey, PUT /api/v1/fleet-adb-key), and hands the private half to a signed-in operator app at GET /api/v1/app/adb-key, audited and rate-limited.
  • AIO Enroll for Android (~/aio-mdm/mdm-enroll-android, commit 79380f5) already does the whole job from a phone: mDNS discovery, try :5555 with the fleet key (State.autoConnect), one-shot probe (Probe.read: serial, maker, model, Android, Device Owner, accounts, users, agent versions), then the eight steps in Enroller.kt — token, install over exec:cmd package install -S, dpm set-device-owner, grants, am start with the token, wait for the server. Uses libadb-android for the adb protocol.
  • The firmware client (com.aioapp.mdm) is a system app with its own WS to the server, a hand-rolled WebSocket, and already proxies adbd bytes (AdbTunnel.java). It has no adb client yet.

So the idea is to move what the phone app does into the T7, and let the server drive it. The phone and desktop apps stay for venues with no T7 and for the lab.

2. How it works

Server

  1. Picks a scout per restaurant: an online firmware device (T7 or kiosk), the one with the longest uptime.
  2. Sends it net_scan over the command WS, carrying the fleet private key for this session only.
  3. Stores what comes back as sightings (serial, host, model, state), shows them in the inbox / on the restaurant page.
  4. On approve: mints a one-shot enrolment token (restaurant = the scout's, class chosen, max_enrolls=1, 10 min) and sends net_enroll.

Scout (firmware client)

  1. Finds hosts: NsdManager _adb._tcp + _adb-tls-connect._tcp, plus a parallel TCP sweep of its own /24 on :5555 (254 connects, a few seconds). The sweep catches vendors whose adbd has mDNS off.
  2. For each open :5555: adb CNXN, AUTH with the fleet key. Refused → "not ours", left alone for an hour. Never answers a key prompt (no AUTH type 3), so no dialog ever pops on a stranger's device.
  3. Accepted → the same one-shot probe as the phone app. Reports a sighting.
  4. On net_enroll: downloads the DPC APK from the server, installs, sets Device Owner, grants, starts the agent with the token, streams progress; the server confirms the enrolment itself.
  5. Drops the key from memory when the scan session ends.

Target (vendor device)

  1. Ships with our public key in /adb_keys, adbd on tcp 5555 from boot, ro.adb.secure=1, no accounts, no Device Owner.
  2. Does nothing. Boots, joins Wi-Fi (vendor's staging or pre-set SSID), is found.
  3. Ends up with aio.app.mdmclient.dpc as Device Owner, enrolled into the restaurant the scout belongs to.

Why the key travels per session, not in the image

The images are public and cloned onto hardware we don't control; a fleet private key baked into them would be in every vendor's hands within a week. The server already seals it and hands it to signed-in operators; a scout is a stronger identity than an operator's phone (platform-signed app, per-device key, known restaurant), so the same rule holds: fetched when needed, held in memory, discarded. It is never given to a DPC device, only to agent_kind = firmware.

The adb client on the T7

Plain-TCP adb protocol v1, ~400 lines of Java, no library (the AOSP tree has no Gradle deps): CNXN / AUTH(token → RSA-SHA1 PKCS#1 signature) / OPEN / WRTE / OKAY / CLSE, one stream at a time, 256 KB max payload. Streams needed: shell: and exec:cmd package install -r -S <size>. No TLS: :5555 is the plain transport, which is the whole point of the vendor ask. The TLS/pairing path (Wireless debugging) stays with the phone app.

Class guess

The server already maps a serial or model to a class for the Enroll apps (POST /api/v1/app/classify, productions). Reuse it: SUNMI D2s → kds, D3 Pro → pos, HK1 RBOX → dongle, ZC-3568K → kiosk, our own serial pattern → "firmware, self-enrols, skip". The guess is a default the approver can change; in auto mode (phase 3) it is the decision.

3. What a scout never does

  • Touch a device that refused the key. Not even a second try inside the hour.
  • Enrol a device with a Device Owner that isn't ours, any account, or a second user — same blockers as enroll-adb.sh; it reports them so a person can factory-reset.
  • Enrol anything without an approval unless the restaurant's auto-enrol switch is on (phase 3, off by default, super admin only).
  • Scan outside its own /24, or any port but 5555 and advertised adb ports.
  • Persist the fleet key. A scout that reboots mid-session asks the server again.
Risk worth naming: a restaurant's Wi-Fi may host a device that trusts our key but belongs to someone else (a vendor demo unit, a returned device that was re-sold). Approval-before-enrol (phases 1–2) is the control; auto mode must stay per-restaurant and off by default.

5. Phases

Phase 0this week

Prove it between two T7s. One on feat/sunmi-mock as the "vendor device", one on the normal image as scout. Hand-written adb client in the firmware client, triggered by a net_scan frame from stage, results in the server log only. Vendor one-pager from section 4 goes out in parallel.

Phase 2approve → enrol

One-click enrol from the dashboard. net_enroll frame, one-shot token minted server-side, progress streamed, enrolled_by = the approver, "via T7 …230" on the device's record. Handles the four lab devices from the dashboard with nobody in the room.

Phase 3zero touch

Per-restaurant auto-enrol switch (demo option D). Class from the server's guess; anything it can't classify waits for a person. Off by default, super admin only, every auto-enrolment audited and shown in the Daily Report.

Phase 4later

Scout also re-enrols a device that lost its agent (factory reset in the field) and flags devices that trust our key but aren't enrolled anywhere. Phone/desktop Enroll apps keep the lab and venues with no T7.

7. Option B in detail — sightings in the onboarding inbox

Picked 8 Oct. The UI decisions inside B are in t7-enroller-inbox-demos.html. This section is the mechanics underneath them.

7.1 A sighting's life

seen ──probe──▶ ready ──approve──▶ enrolling(step 1..8) ──▶ enrolled   (row leaves the inbox; device appears at the venue)
   │                │                       └──fail──▶ failed(reason)   (row stays, "Try again")
   │                ├──▶ blocked(reason)   account / foreign Device Owner / second user — "Check again" re-probes
   │                ├──▶ ours              AIO serial pattern: firmware, enrols itself — folded under the venue, no action
   │                └──▶ elsewhere         already enrolled on this server (or a peer) — not shown; counted
   └──refused──▶ (not stored as a device; the venue header counts it, retried after 1 h)

stale: not seen by any scan for 24 h → row fades;  7 days → row removed (it comes back if seen again)

7.2 Data

sightings
  id, restaurant_id, scout_serial, host (inet), port,
  serial, manufacturer, model, android, owner_pkg, owner_ours, accounts int, users int,
  dpc_version, firmware_version,
  state  text  -- ready | blocked | ours | enrolling | failed
  reason text, class_guess text, class_confidence text ('catalog'|'model'|'none'),
  first_seen, last_seen, approved_by, approved_at, job_id (→ commands)
  unique (restaurant_id, serial)

restaurants + scan_enabled bool default true, auto_enroll bool default false (phase 3)
devices    + enrolled_via_serial text   -- the scout, for "via AT070AA2600030"

Refusals are kept in memory on the scout only (host → until), never sent up: a device that refused our key is not ours to list.

7.3 Frames (command WebSocket, firmware client ≥ 1.9.0)

server → scout   {"type":"net_scan","session":"…","key_pem":"…","subnet":"auto","ttl_s":600}
scout → server   {"type":"net_sighting","session":"…","host":"10.32.1.13","port":5555,
                  "serial":"D2S99120","manufacturer":"SUNMI","model":"D2s","android":"11",
                  "owner":{"set":false,"ours":false,"pkg":""},"accounts":0,"users":1,
                  "dpc_version":"","firmware_version":null}
scout → server   {"type":"net_scan_done","session":"…","hosts":254,"open":6,"accepted":4,"refused":1}

server → scout   {"type":"net_enroll","job":"…","host":"10.32.1.13","serial":"D2S99120",
                  "class":"kds","token":"enr_…","apk_url":"…","apk_sha256":"…","key_pem":"…"}
scout → server   {"type":"net_enroll_progress","job":"…","step":3,"text":"Setting Device Owner…"}
scout → server   {"type":"net_enroll_done","job":"…","ok":false,"reason":"set-device-owner: …"}

key_pem rides inside the frame, so a scout holds it only while a session or job is live; the server logs fleet_adb_key.scout with the scout serial each time it sends one. The server verifies the enrolment itself (the device's own POST /api/v1/enroll with that token), so a scout's "ok" is a hint, not the record.

7.4 Server side

  • Scout picker: per restaurant, the online agent_kind=firmware device with the longest uptime, client ≥ 1.9.0, Wi-Fi (not hotspot). Kiosks count as scouts unless you say T7-only.
  • Schedule: one scan per venue every 15 min inside service hours, every 2 h outside; plus "Scan now" from the inbox (operator or above, 1/min per venue). A venue with no online scout shows "no Tableside AI online here".
  • Approve = one command: POST /enrollment/sightings/{id}/enroll {class} → mints a hidden profile token (name "scout · venue · serial", max_enrolls=1, 10 min, restaurant set) → net_enroll to the scout → the job shows under /commands as type net_enroll with the eight steps as its delivery log. "Enrol all" is N of these, sent to the one scout in sequence (one adb install at a time keeps the Wi-Fi honest).
  • Class guess reuses the Enroll apps' classify (productions, then a model table: SUNMI D2s→kds, D3 Pro→pos, HK1/RBOX→dongle, ZC-3568K→kiosk). Confidence drives the row: a catalog hit is pre-selected, a model hit is pre-selected with "guess", none leaves the select on "— pick —" and keeps the venue's Enrol-all from including it.
  • Permissions: see sightings — any dashboard role that sees /enrollment; approve — operator and above (same as the Enroll apps' token mint); scan settings and phase 3 switch — super admin.
  • Trail: devices.enrolled_by = approver, enrolled_via_serial = scout; audit device.enroll "via AT070AA2600030"; the Recent enrollments table gains a "via" column; the device page says "Enrolled by hw · via Tableside AI AT070AA2600030".

7.5 Scout side

  • Runs the scan in a foreground thread with a Wi-Fi lock, 16 connects in parallel, 400 ms connect timeout: a /24 takes ~7 s. Skips its own address and anything in the refused cache.
  • A probe is one shell stream (the phone app's Probe.read, markers between sections) — about a second per device.
  • Enrol: APK streamed from the server straight into exec:cmd package install -r -S, never written to the T7's disk; the eight steps and their timeouts copied from Enroller.kt / enroll.rs.
  • Pauses while a guest is using the tablet (screen on and unlocked for the T7's own app) — a scan is background work, not a reason for a stutter at the table.

  4. Trail (device page, recent table), restaurant-page slice, stale/removal rules, "Check again".
