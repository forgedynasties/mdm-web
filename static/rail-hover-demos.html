Two rails, one width

Your idea, built so you can feel it: on a page that has its own rail, the app rail sits collapsed, and hovering it expands it while the child rail shrinks — so the content never moves. Below are three ways to resolve the same collision. Hover the narrow icon strip in each mock.

1 · Reciprocal — they trade placeshover the iconsmy pick

App rail 56→196px, child rail 196→56px, at the same time. Total chrome width is constant, so the device list never reflows. The child rail keeps initials while collapsed, so you can still see which venue is selected.

the device list — it does not move when you reach for the nav
Good at Nothing reflows, which is the whole point: reaching for navigation should not make the thing you were reading jump. The child rail stays legible as initials, so you do not lose your place in it either.
Bad at Two things animate at once, which can read as busy. Needs :has() or a few lines of JS, and the initials only work for short names — "Harbor Grill" and "Harvest Grill" are both HG.

Good at Simplest to build and the calmest — one element animates, nothing else is aware of it. Works the same on every page that has a child rail, with no coordination.

What it needs beyond hover
Three rules, whichever option wins · Hover cannot be the only way in. Keyboard focus must expand it too (:focus-within), or the rail is unreachable by tab — and on a touchscreen there is no hover at all, so it stays expanded there. · A small delay before expanding (~120ms) and a slightly longer one before collapsing, or the rail flickers every time the pointer crosses it on the way to the content. · A pin. Someone working in the nav for a minute should be able to lock it open; the state sticks per person. I would ship 1. It is your idea and it is the only one where the thing you are reading never moves — and the child rail collapsing to initials keeps the current filter visible, which the overlay loses. 2 is the fallback if the double animation feels busy in practice.
