Once Actions is gone, where do multi-device actions live?

Install, uninstall and client update now start from the app (the store, shipped on stage). Kiosk, boot logo and OTA already have pages. Reboot exists per device. That leaves one group with no noun to live on: shell, screenshot, collect logs, query, wipe, unenroll — across many devices. "Run this on these forty tablets" is about a set, not about a thing.

What already exists, and changes the answer: the Devices page has had multi-select all along — checkboxes, a bulk bar, "select all N matching this filter" across pages, and six bulk routes (bulk-restaurant, bulk-nickname, bulk-class, bulk-retire, bulk-kiosk, bulk-kiosk-apps). Its Reboot, Screenshot and Install buttons do not act: they hand off to Actions prefilled (bulkGo('/commands', {type:'reboot'})). So the selection machinery for option 2 is built; what is missing is doing the work in place instead of bouncing.

I would build 2, then the Jobs page, then delete Actions — in that order, because the hand-offs break the moment the route goes. Option 1 is the cheap path and I would not pick it: it keeps the thing we are trying to remove and only hides it. Option 3 is where this probably ends up in practice, but starting there means building the wizard before knowing whether anyone misses it — so I would ship 2, leave the fleet-wide cases on /schedules and the store, and add a wizard only if something turns out to have no home.

One correction to my earlier plan: I proposed a Power & reboot page. The code does not support it — reboot_behavior='scheduled' exists only as an OTA deployment policy (updates + update_devices), and recurring sends come from scheduled recipes. There is no fleet reboot-window feature to put on a page, so a Power page today would hold one button that already exists on the device page. Dropped.
