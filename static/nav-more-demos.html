“More” — five ways to hold 28 pages

The directory fixed reachability and created a new problem: a 520px, four-column, 28-link slab hanging off a dock button. It is a page pretending to be a menu, and it gets worse with every page we add. Five alternatives below, each mocked in a working frame — click the dock, they all actually open, filter, drill and pin. The current one is included first, at real size, so the comparison is fair.

The constraint that matters: 28 today, and the route table grows. Judge each option by what it looks like at 40.

The slabReplaced by A

Four sections, two columns, everything visible at once. It solved the real problem — nothing is unreachable any more — by showing all of it, all the time. At 28 links it is already the largest surface in the product that is not a page.

Option A
Type-to-goChosen · shipped

More opens a single narrow column with the cursor already in a search field. Above the fold: the six pages you actually opened recently. Type and it filters all 28 — and all 40, and all 100 — down to what matched. This is the ⌘K palette you already ship, scoped to pages and given a mouse-reachable door, so it is one navigation behaviour rather than two that drift apart.

Option B
Two steps

More opens four rows — Fleet, Deploy, Control, Admin — with a count on each. Pick one and the panel replaces itself with that section's pages. Never wider than 236px, never taller than nine rows, whatever the page count does, because a new page lands inside a section instead of on the surface.

Option C
The dock follows you

The four core links stay. A fifth slot shows the section you are currently working in — on any Fleet page it reads “Fleet ▴” and opens the six Fleet pages; on a rollout it becomes “Deploy ▴”. More shrinks to the handful that belong to no section. The menu you open is almost always the one you wanted, because where you are predicts where you are going.

Option D
Full sheet

Stop pretending it is a menu. More opens a surface over the whole page: search at the top, recents as pills, all four sections in four columns at a readable size. It is bigger than the slab on purpose — the difference is that it is a mode you enter and leave, not a popup dangling off a button, so it can use the room honestly and it is the same object on a phone.

Option E
Pin what you use

The dock's four are fixed; everything after them is yours. Pin a page and it joins the dock. More holds the rest as a compact list, each row with a pin. The menu shrinks as you make it yours, and two people doing different jobs stop sharing one compromise.

Decision
A is built and on stage. More no longer renders a menu: it opens the command palette in pages mode — the same object ⌘K opens, scoped to navigation, 420px wide. The empty state is B's spine (recent pages, then the four sections as one row each, which type their own name when picked), so browsing still works before you know what anything is called.

The directory markup did not go away — it is #page-index in layout.html, hidden and never rendered, and the palette reads its page list straight out of it. That matters: the per-entry role guards are still the server deciding what each person can reach, unchanged. Recents come from the route handler that already fires on every navigation, so there is no new bookkeeping, and a page your role can no longer open silently drops out of your own recents.

⌘K on an open pages-mode palette widens it back to everything rather than closing it.

Still deliberately not built: C and E, for the reason below — and E is worth revisiting once A has been live long enough to see whether everyone's recents are the same two pages.
The reasoning
Ship A. It is the only option whose size does not move when the route table does, and that is the actual problem — the slab is not too big for 28 pages, it is too big for a number that keeps growing. It also costs the least: the matching, the ranking and the keyboard handling already exist in mdmOpenPalette; More stops rendering a menu and opens that instead, filtered to pages. One navigation behaviour, two doors.

Then steal B's spine for the empty state. A's genuine weakness is the first run, before there are recents and before you know what anything is called. Show the four sections collapsed to their names under the search field when the box is empty — so a new person browses like option B, and everyone else types and never sees it.

I would not ship C or E yet, not because they are wrong but because they are both bets on behaviour we have not measured. E in particular is worth revisiting after A has been live a while: if the recents list turns out to be the same two pages for every person, that is the argument for pinning, made with evidence instead of a guess.

D is the one to keep in the drawer. If the page count doubles, or the phone experience becomes a priority, D is the answer and A is not.

All five mocks are live: real open/close, real filtering in A, real drilling in B, real context switching in C, real pinning in E. They use style.css tokens, so the theme switch top-right renders every one in both themes. Footprints in the table are measured from these mocks at this page count, not estimated.
Nothing here is wired to the app — picking one is the point, and no dashboard code changes until then.
