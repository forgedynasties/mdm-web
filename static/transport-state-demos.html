Reporting but unreachable — how the dashboard should show it

A firmware device whose WebSocket is gone keeps checking in over HTTP. Its telemetry is current, its battery and temperatures are live, "Last seen" says just now — and the badge says Offline, because the badge is live socket presence. Nothing anywhere says the thing that matters: commands sent to it will not run. That is what took a day to find on AT070AABU00077 (9 Oct 2026: 15h of check-ins, a shell command stuck at delivered).

With client 1.9.5 the server hands pending commands back in the check-in response, so such a device is reachable but delayed. On a client older than 1.9.5 — including every v2.0.x device, which cannot take the qcom-signed build — it is not reachable at all. The UI has to tell those two apart, because one is a note and the other is a truck roll. Pick one.

Option A
Third badge stateclosest to today

Online / Offline becomes Online / No control / Offline. One badge, one place, every page that already renders the badge gets it free. The amber state means "alive and reporting, but we cannot command it".

AT070AABU00232 Online just now · 41° · 68%
AT070AABU00077 No control just now · 39° · 93%
AT070AABU00318 Offline 6h ago · — · —
Good at One vocabulary, no new column, no layout change. The contradiction ("Offline · just now") disappears on its own. Sorts and filters that group by status keep working.
Bad at Folds "delayed but reachable" and "cannot be reached" into one amber badge — the operator still has to open the device to learn which. Three states is the most a single badge can carry before it stops reading at a glance.
Option B
Badge stays binary, transport is its own chipmy pick

Online/Offline keeps meaning exactly what it means today — live socket — and a second chip names the channel: WS, HTTP only, or No channel. The two facts stay separate because they are separate, and "HTTP only" vs "No channel" is visible without opening anything.

Good at Says precisely which of the three situations a device is in, in the roster, without a click. The filter row is the fleet-wide number — the thing that would have shown this the day it started. Nothing existing changes meaning.
Bad at Two badges per row costs width and a little noise on a page already dense with chips; a healthy fleet shows a "WS" chip on every row that carries no information. (Fixable: render the transport chip only when it is not WS.)
Option C
Device page banner only

Leave the roster alone. The device page carries a banner, worded for whoever opens it, and the fleet learns about it through the alert instead of the badge.

AT070AABU00077 Offline Last seen just now · v2.1.024 · client 1.8.9
⛔Reporting, but nothing can be sent to it No WebSocket for 15h 12m while still checking in every 5 minutes. This client takes commands over the socket only, so anything queued for it will sit at delivered and expire. Its socket thread is gone — a reboot is the only thing that brings it back.
⚠️Commands are going over check-in No WebSocket for 41m. Client 1.9.5 takes commands in the check-in response, so this device is reachable, roughly a minute behind. Remote screen and adb tunnel need the socket and will not work.
Good at Room to explain, and to say what to do about it — the only option that can carry the "a reboot is the only fix" sentence. No roster changes at all.
Bad at Invisible until someone already suspects that device. The fleet page keeps showing the same contradiction that cost a day. Really a complement to A or B, not a rival.

Deployed today: none of these — the dashboard has only Online/Offline from live socket presence. I would ship B plus C's banner. B because the two facts the operator needs (is it alive, can we command it) are two facts, and folding them into one badge is what hid this; the chip is suppressed when it is plain WS, so a healthy fleet looks exactly as it does now. C because when a device is in the worst state the page has to say that a reboot is the fix, and a chip cannot say that. A is the cheap version if the roster must stay single-badge.
