Keeping clients up to date — a setting, not a button

"Update all behind" is a one-shot command issued to whoever happens to be online at that second. On a restaurant fleet that is most of the fleet missing: devices are off overnight, boxes sit unplugged for a week, a venue's wifi is out at the moment you press it. What is actually wanted is a standing instruction — this slot should be on this build — that each device satisfies the next time it checks in. The hosted build already tells the server what the target is; what is missing is permission to act on it, and the visibility that comes with having a target.

Today on stage now

A button on the Clients page: Update all behind with a count. It queues an install for the devices that are behind right now and does nothing for anyone offline, so the number never quite goes to zero and someone has to remember to come back and press it again. There is no record of intent anywhere — only a pile of commands.

A · Auto-update toggle per slot my pick

One switch per client: keep devices on the hosted build. With it on, any device that checks in behind the hosted build is handed it then and there — tonight, next week, whenever it comes back — and the page shows the standing target rather than a button. A window keeps it out of service hours, and a pause stops it without forgetting the setting. Good: matches how the fleet behaves, needs no one to remember, and "behind" becomes a queue that drains by itself. Bad: a bad build reaches everything with no second gate; the pause and the staged option below are the answer to that.

B · Staged rollout, the way firmware already works

The same standing target, but it widens in steps: a canary group first, then a percentage, then everyone, each step gated on the previous one reporting healthy. Good: a bad client build stops at the canary instead of the fleet, and it reuses the rollout machinery and vocabulary the firmware side already has. Bad: heavier to operate for what is usually a small APK, and a stalled stage needs someone to notice and push it along.

C · Keep the button, make it a standing order

The smallest change: the button stays where it is, but pressing it records "everyone should be on 1.9.6" instead of queuing commands for whoever is online. The row then reads as a target with a progress bar, and devices catch up as they appear; pressing it again is a no-op rather than a second pile of commands. Good: one afternoon's work, no new surface, fixes the actual defect. Bad: still a press per build — nobody is told when a new client is hosted, so a build can sit unrolled for a week.

D · Per-venue policy

The target is set per venue or group rather than per fleet: a pilot restaurant tracks the newest build, everyone else tracks the one proven there. Good: the real-world shape of a pilot, and the one that matches how firmware is piloted on 022 today. Bad: the most moving parts of the four, and it answers a question ("which venues pilot?") that nobody has asked for the client APK yet.

Pick: A, with C as the first step. A toggle per slot is the honest model — the hosted build is already a declaration of intent, and this just lets the server act on it when each device actually appears. C is the same idea with a tenth of the work and can ship first; B is worth adding once the DPC fleet is big enough that a bad client build costs a site visit. D should wait until someone asks for it.
