More graphs on the Server page

Four options, all drawing live-shaped data so you can judge the density rather than a picture of it. The important thing first, because it decides most of this:

The page already collects an hour of history and shows you four minutes of it. metrics.Collector keeps seriesLen = 360 samples at 10s — one hour — of requests/s, check-ins/min, WebSockets, goroutines, heap MB, sys MB, DB pool used/total/waiting. The tile sparklines render vals.slice(-36). Ninety percent of what is already measured, already streamed to the browser, is thrown away at draw time. Options A, B and C cost no new collection at all — they draw data you are already paying for.

What is not in the series, and would need the collector extended: error rate per sample (only lifetime counters exist), queue depths (commands pending, OTA in flight, alerts open — sampled per tick but never stored), and the Postgres vitals (cache hit, connections, longest query). Option D is about those.

Option A
One big chart, tiles become its legendNo new dataMy pick

Keep the six tiles as the numbers, and put one full-width chart under them showing the whole hour. Clicking a tile toggles its series in and out. This is the smallest change that stops discarding 90% of the history — same payload, same SSE frame, one chart component.

Last hour
Good at
  • Shape over an hour — a sparkline cannot show you a ramp, a plateau or a sawtooth.
  • Overlaying series is how you spot that check-ins and DB pool move together.
  • Reuses the tiles you already have as the legend. No new vocabulary.
  • Zero server work: the data is already in the frame.
Bad at
  • Units collide. Requests/s, heap MB and goroutines on one y-axis means everything is normalised and the axis stops meaning anything.
  • More than three series at once is a plate of spaghetti.
  • Adds ~250px above the fold, pushing queues and routes down.
Option B
Small multiplesNo new data

Every series gets its own little chart, all sharing one x-axis, all the same size. No toggling, no legend, no shared y-axis problem — you read down the column at a fixed point in time and see what every metric was doing at that moment.

Good at
  • Each metric keeps its own scale, so each chart is honest about its own units.
  • Scanning for "which one of these is the odd shape" is genuinely fast.
  • Adding a metric is adding a cell — it does not degrade the others.
  • Handles 8 or 14 series where option A falls apart past 3.
Bad at
  • Comparing two precisely means eyeballing across two boxes.
  • Each chart is small — fine for shape, poor for reading a value.
  • Duplicates the tiles unless the tiles are absorbed into it (which this mock does).
Option C
Correlate two, properlyNo new data

One chart, exactly two series, one on each y-axis with its own scale and its own labelled ticks. Pick which two. This is the chart you actually want during an incident — "the pool saturated, did check-ins spike first?" — and it is the one question the sparklines cannot answer.

Compare against
Good at
  • Dual axes mean both series are readable in their real units — no normalising.
  • Answers the causal question, which is the actual reason anyone opens this page mid-incident.
  • Small: one chart, two dropdowns.
Bad at
  • Dual-axis charts invite false conclusions — two lines can be made to look correlated by scaling alone. The correlation number shown here is a partial guard, not a cure.
  • Requires the operator to already have a hypothesis. It answers a question; it does not raise one.
  • Useless as an ambient display — nobody leaves it open.
Option D
Graph the things that explain an incidentNeeds collector work

The existing series are all host metrics — heap, goroutines, pool. None of them tell you a rollout stalled. This option extends metrics.Sample with the things the page already computes every tick but throws away: queue depths, error rate, DB vitals. Drawn as compact horizon strips so a dozen fit without a dozen charts' worth of room.

What this needs: ~6 new fields on Sample (errors/s, commands pending, OTA in flight, alerts open, cache hit %, connections), all already available at sample time — the queue counts come from serverQueues() and the DB vitals from the 30s-cached pgStats(). Errors/s is the only genuinely new instrumentation: routeAgg counts errors for the lifetime of the process, not per sample, so the collector needs a per-tick delta. Cost: one afternoon, ~40 lines in internal/metrics. Memory is unchanged in practice — 360 samples × 6 float64 is 17KB.
Good at
  • These are the metrics that make this page different from a generic host monitor.
  • "Alerts open climbed while OTA in flight sat at zero" is a sentence no heap graph can produce.
  • Horizon strips fit ~12 metrics in the height of one ordinary chart.
  • Error rate over time is the single most useful missing number on the page.
Bad at
  • Only option here that needs server changes, so it cannot ship this afternoon.
  • Horizon charts need a legend and a moment's learning — they are dense, not obvious.
  • Sampling pgStats() into the series ties the series' honesty to a 30s cache.

What I would do
A now, D next, and B instead of A if you want more than three series.

A first because it is free. The history is already collected, already streamed, already in the browser — it is being thrown away in a .slice(-36). Drawing it costs one chart component and no server change at all, and it is the difference between "requests are at 12/s" and "requests have been climbing for twenty minutes".

Then D, because it is the only option that adds information rather than rearranging it, and because error rate over time is the most obviously missing thing on a page whose job is to tell you the server is unwell. Everything it needs is already computed each tick and discarded — the work is storing it, not gathering it.

C is a good chart and the wrong default. Build it as a mode of A (two-series mode flips on the second axis) rather than as its own block — the dual-axis honesty problem is real, and it should be something you deliberately switch into, not something the page shows you unprompted.

Not A and B both. They answer the same question at different densities; shipping both means the same data drawn twice on one page. If the series count grows past about six — which D would do — then B replaces A rather than joining it.

Charts are inline SVG drawn from generated data with the real series' shapes and ranges; no chart library, so nothing here implies a dependency choice. They use style.css tokens, so the theme switch top-right renders them all in both themes. A, B and C would draw the exact payload the page already receives — snapshot.series, 360 samples, in every SSE frame.
