Removing the hardcoded device key from the firmware client

A plan, 30 Sep 2026. Nothing here has been changed yet. The figures are from live today.

Why this matters now. The firmware client (aio-mdm-client, a public repository) has a built-in default device key in MdmApiService.java, and the live server's DEVICE_API_KEY is that same value (checked today by comparing hashes, without printing it). The server's own comment in internal/middleware/auth.go says what the key allows: it proves only "some device in the fleet", so anyone with it can check in as any serial, and can open the WebSocket as any serial and receive the commands pushed to that device. It is in public git history, so it has to be treated as public from now on; deleting it from the source does not un-publish it.

What already exists and can be reused:

  • Per-device keys on the server. DeviceAuth accepts either the shared key or a per-device dvk_… key (stored as a SHA-256 hash, devices.device_key_hash). With a per-device key, the request is bound to that serial and requireBoundSerial refuses acting as another. DPC devices get one at enrollment.
  • A key override on the device. Since 6 Aug the client reads persist.sys.mdm.api_key before its built-in default, and re-reads it on refresh.
  • Client self-update since 1.0.0, and firmware OTA for everything older.

Why the shared key can't simply be rotated today: every one of the 177 firmware devices sends the built-in value. Changing DEVICE_API_KEY would cut all of them off at once, and the 156 older ones could only be brought back on site or by an OTA they can no longer download.

The plan: give every device its own key, then retire the shared one

Old clients keep working at every step until the last one is gone. The shared key stops being an identity and becomes, at most, a way for a brand-new device to introduce itself.

Phase 1Server only: contain the shared key (days)

  • Lock a serial once it has its own key. A request using the shared key for a serial that has a per-device key is refused, including the WebSocket. No existing device changes behaviour; it closes impersonation for every device the moment it migrates.
  • Flag impersonation. The same serial connected twice at once, from two addresses, or with two boot ids raises a critical alert (these are rare in normal operation).
  • New serials via the shared key go to the enrollment inbox as "unverified" instead of joining the fleet silently, so a made-up serial can't appear as a real device.
  • A count on the Clients page: devices still on the shared key, by client version, so progress is visible.

Phase 2Client 1.6.0: devices get their own key (1–2 weeks)

  • On start, if the client has no stored key, it generates one on the device (32 random bytes, kept in Android Keystore-protected storage, never in a system property) and registers it: POST /api/v1/device-key with its serial, boot id and build, authenticated with the shared key.
  • The server accepts the registration once per serial (first come; the moment it is taken, Phase 1 locks the serial) and only when the claim is consistent with what it already knows: the serial exists, it is connected or checked in within minutes from the same address, and its build and boot id match its last report. Anything else is refused and alerted.
  • From then on the client sends X-API-Key: dvk_…. If the server says the key is unknown (for example after a database restore), the client falls back to the shared key and re-registers, which Phase 1 turns into an admin-visible event rather than a silent swap.
  • Recovery: a device that loses its key (factory reset, data wipe) can't re-register a locked serial. The device page gets Reset device key (admin): it opens a 30-minute window in which that serial may register again.
  • Rollout: first the 21 devices that self-update, by the usual path (stage, pilot device 022, then live). They show up on the Clients page as having their own key.

Phase 3Firmware: the older 156 devices (with the next OTAs)

  • The next QCOM (v2.1.x) and GMS (v2.0.x) images ship client 1.6.0, so the devices that can't self-update get it with their next firmware update, and from then on update themselves.
  • New images stop carrying the public default. The build injects the shared (enrollment) key from the build machine, like the publish key is kept today (~/.config/aio-mdm/, never committed), as a read-only property the client reads first. The source keeps the old default only as a last fallback so an old checkout still talks to an old server.
  • Devices that sit on old firmware and never take an OTA stay on the shared key; Phase 4 decides what happens to them.

Phase 4Retire the shared key (when the count reaches zero, or a set date)

  • When no active device is left on the shared key, set the server to accept it only for registering brand-new devices, and only into the enrollment inbox for approval.
  • Then rotate DEVICE_API_KEY to a new secret that only new images carry. Devices already on their own key don't notice.
  • Anything still on the old key after the cut-off shows on the Clients page and in the enrollment inbox; bringing it back means an OTA or a technician visit.

Risks and how the plan handles them

  • Someone registers a key for a serial before the real device does. The registration checks (connected now, same address, matching build and boot id) and the alert on any refused or conflicting claim make this visible; Reset device key repairs it. Starting with the 21 self-updating devices keeps the window small and watched.
  • A device loses its stored key. Covered by the reset window; the client never gives up, it keeps checking in with the shared key until an admin opens the window.
  • An OTA takes weeks to reach old devices. Phases 1–2 already close impersonation for every migrated device, so the risk shrinks as each one moves, not all at once at the end.
  • Stronger option, later: Android key attestation (a hardware-held key, signed by the device's secure element) would make registration unforgeable. It depends on the attestation roots in our AOSP builds, so it is worth a check on one QCOM and one GMS device before relying on it.

Suggested order of work

  1. Phase 1 server changes, deployed to stage then live.
  2. Client 1.6.0 key registration, and the server endpoint and reset button, tested on stage with pilot 022.
  3. Roll 1.6.0 to the 21 self-updating devices; watch the count and the alerts for a week.
  4. Build the next QCOM and GMS images with 1.6.0 and the injected enrollment key; release as usual.
  5. Set the Phase 4 date once the count is low.
