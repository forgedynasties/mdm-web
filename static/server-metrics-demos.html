Server metrics — what to show and where

A live view of what the MDM itself is doing: load, throughput, and where the time goes. Everything mocked below is measurable from what the server already holds — the WebSocket hub knows its connections, the pgx pool reports its own stats, the Go runtime reports goroutines, heap and GC, and the request path can be counted with a middleware wrapper. Nothing here needs Prometheus or a second process.

Four options, from a strip that hides in the existing header to a full page. Pick one — and note the last section, which is about what "live" should mean.

Group 1 — where the metrics live

A · A live strip on the existing Health page smallest

Six numbers in one row, refreshed over the SSE stream the dashboard already opens. No new page, no nav entry.
healthy uptime 6d 04h WS 31 check-ins 42/min p95 84 ms DB pool 6/25 heap 212 MB goroutines 487
Good at Free to build and free to look at — it sits where you already go when something feels wrong. Enough to answer "is the server itself the problem?"
Bad at No history, so you cannot see that p95 tripled an hour ago. One bad row and you still have nowhere to click.

C · One big chart, everything else underneath

A single stacked request-rate chart over 6 hours as the page's headline, with tiles demoted below it. Reads like a monitoring tool.
device APIdashboardpeak 04:10 — an OTA deployment to 22 devices
Good at Shape over time is what tells you something changed; a spike lines up with what caused it.
Bad at One chart answers one question. Everything else gets pushed below the fold, and the chart is the most work of anything here.

Group 2 — how live is live

E · Push over the existing SSE stream, 2-second tick my pick

The dashboard already holds an event stream open. Metrics ride it as one more event type, so there is no polling and no second connection. Sparkline history comes from a ring buffer in the server (one hour at 10-second resolution is ~360 points per series, kilobytes).
Good at No new transport, no new dependency, and the numbers move while you watch — which is the whole point of asking for live.
Bad at History dies with the process. Fine for "what is happening now", not for "what happened on Tuesday".

F · Persist a metrics row per minute

Same collection, written to a table and trimmed on the housekeeping loop. Survives restarts and deploys; lets the page show yesterday.
Good at Post-mortems. "The box wedged at 3am" becomes answerable.
Bad at Writes to the same Postgres the metrics are measuring, on a t2.medium that is already tight. Worth doing only for a handful of series, not everything on the page.

My pick: B + E, with a slice of F. B because the queues section is the part no external monitoring tool would give you — it knows what an OTA deployment or a peer outbox is. E because it is free: the stream is already open. And a narrow F — say six series at one row per minute, kept 14 days — so a slow morning can be looked at after the fact without turning the MDM into a time-series database. D is worth adding later as a tab inside B, since it shares the same event stream.
