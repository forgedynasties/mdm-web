Device role model: plan

The MDM was built around the firmware and testing teams' lab work: install any APK, free shell, bulk screenshots. Restaurants need the opposite. Every device has one job, runs one AIO app, and must stay on the current prod build of that app without anyone pressing a button. This page fixes the model before any UI is drawn. It builds on the command-model audit (3 commands, 3 sessions, the rest is config). Words in quotes are placeholders; naming is a later pass. Drafted 14 Oct 2026 from the Q&A with you.

1 · Decided

Role decides the appMany hardware models map to one role, detected automatically. One AIO app per role, nothing else in the foreground.
Two states, set by venueAssigning a venue makes a device "deployed". Removing the venue makes it "undeployed" and unlocks it. Moving venue keeps it deployed.
Deployed = latest prodAll venues run the latest prod build of their role's app, and the latest prod firmware for their hardware. No pilot venues. No app rollback.
Lab devices get slots and a debug flagRelease slots are per role. Debug tooling appears only on debug-flagged devices. The hardware testing team manages the app inventory.
Lock follows roleA deployed, non-debug device is always locked to its role app. It can still be exited on the device.
MDM never configures the appNo managed config, no backend URL, no venue data pushed into the app. The app sorts that out with its own backend.
Alerts come from MDMNobody relies on restaurant staff calling. MDM must notice a broken device first.
Hide in UI, keep in backendLab features leave the dashboard for deployed devices but keep their handlers and API, so a change of plan is a UI change only. Same precedent as the boot logo.

Delivery: one big change on the stage branch, deployed to stage. Live is not touched until you say so.

2 · The model

Role
What the device is for

Today's device_class keys (t7, kiosk, dongle, kds, pos, mpos, payment). Each role names one app family, e.g. TSAI → Nugget.

State
Undeployed / deployed

Derived, not stored: has a venue. One fewer field to fall out of sync.

Channel
Prod, slot 1, slot 2…

Per role. A deployed device follows prod, always. A lab device follows the slot it is put on.

Role detection

A model → role table replaces today's substring guesser (product.ClassForModel), which matches tokens like d2 and t3 and gets things wrong. Our own hardware stays catalog-driven: a T7 is always TSAI, a Kiosk 18/22/27 is always a kiosk. Stock hardware is matched on exact manufacturer + model, several models per role:

An unknown model lands in "role needed" in the enrollment inbox, exactly as an empty class does today. Adding it to the table is an admin action on the dashboard, so it never needs a deploy. A per-device override stays for the odd unit.

App inventory and channels

software team ──upload APK──▶ MDM app library (per role's app family) │ testing team ──promote build──▶ role channel: prod │ slot 1 │ slot 2 │ reconciler (every minute) ──▶ deployed devices → prod ──▶ lab devices → their slot, or left alone

The reconciler is a clone of client_autoupdate.go, which already works: present devices only, behind the target, inside their own timezone's window, 20 per tick, skip anything installing. The diff it acts on is the existing app coverage code. Firmware uses the same shape: one prod build per hardware for deployed devices, fed by the OTA deployments that already reconcile per device.

Variants are separate packages. Nugget ships as aio.app.nugget, aio.app.nugget.internal and aio.app.nugget.uatv2. Android treats those as three different apps that can sit side by side. If slot 1 means "uatv2", a lab device moving between slots would end up with two Nugget apps installed unless the reconciler also removes the other variants. See question 1 below.

Lock

Lock rules collapse into the role. A deployed, non-debug device is locked to its role app's package for its channel. The lock rules page and per-device overrides stay in the backend, and the dashboard stops offering them for deployed devices. The on-device exit stays, with the existing unlock code. When a device re-locks after an exit is still open.

Alerts

Today's alerts cover offline, crash, battery_low, storage_low and control_stale. They fire for every device, lab included. Under this model:

  • Only deployed devices page anyone. A lab unit going dark at 6 pm is normal.
  • New: role app not running. The device is online but its app is not in the foreground, or not installed.
  • New: stuck behind prod. The device is present and inside its window, but the install keeps failing.
  • New: unlocked too long. A deployed device is out of lock for longer than a set time.

4 · Build order on stage

  1. Model → role table with an admin page, replacing the substring guesser. Role → app family mapping.
  2. Channels. A role_channels table (role, channel, app build, set by, at). Promote and demote in the app library.
  3. Reconciler for apps, cloned from client auto-update. Deployed → prod. Lab → slot.
  4. Lock from role. The lock reconciler reads role + channel instead of lock rules for deployed devices.
  5. Debug flag on devices, admin-only, audited. The UI gating from the table above.
  6. Firmware prod pointer per hardware, with live membership on deployments (audit step 2).
  7. Alerts limited to deployed devices, plus the three new kinds.
  8. Demos first for the device page, the app library with channels, and nav. Nothing visible is built before you pick.

Audit steps 1 and 2 (one command catalogue, one scope resolver) come first. Step 3 above is the audit's "app rules", narrowed to role + channel.

5 · Decided in round two (14 Oct)

A slot holds a build or a variantEither a newer build of the prod package or a variant package such as uatv2. The reconciler keeps exactly one package of the role's app family on the device, removing the others.
Builds arrive as a linkThe software team sends an APK link to the testing team, who puts it on a slot or promotes it. MDM gets an "Add build from link" box and a "new builds" inbox. One person can promote; no second approval.
Debug is allowed at a venueWith an expiry, default 24 h, and a banner on the device page. When it ends the device returns to prod and lock by itself.
Rollout = quiet windowProd builds roll out like client auto-update today: present devices, inside their own window, 20 per tick. No staged percentage.

5b · Decided in round three (14 Oct)

Lab work happens in a separate lab view"Open in lab" on the device page, entered by choosing how long (default 24 h) and giving a reason. The device page keeps no lab tools. Demo.
Firmware releases are set per roleA role switch says whether firmware releases apply to it. Even when on, they apply only to the role's devices on the Firmware client (in-house hardware). Standard-client devices (stock hardware) in the same role follow the app channel only. The switch says whether firmware applies to the role. The client type says whether a device can take it.
Firmware releases are per model, not per roleA role can mix our hardware and another company's (self-order kiosk: Kiosk 18/22/27 on the Firmware client, ZC-3568K on the Standard client). The firmware switch lives on each model row in the Role table. Firmware builds belong to one model (product key). The app stays per role. This replaces the per-role switch decided earlier the same day.
Releases page is the pipelineInbox → Slot 1 / Slot 2 → Prod lanes, roles in a list on the side (option B). App lane per role, firmware lane per model with model chips. Worked out.

5c · Decided in round four (14 Oct)

Lab channels are package variantsProd is the base package (aio.app.nugget). internal, uatv2 and so on are their own packages and their own columns. Leaving lab swaps packages, so the no-rollback rule never forces an in-place downgrade.
Firmware per model: Prod, Lab only or OffT7 is Prod. Kiosk 18/22/27 are Lab only for now, with no prod firmware and no gating; deployed kiosks keep what they have. Stock models are Off. Firmware changes in lab are off-venue only.
No migration logic in the reconcilerProd moves a device only within its firmware line. The 101 T7s on v2.0 migrate through two watched rollouts (v2.0.997, then v2.1.022) using the existing rollout tools. After that they follow prod by themselves, and no bridge code is left to delete.
Live facts checkedv2.0.997 and v2.1.022 are published T7 releases on live. Kiosk 22 has its own v1.1.x line; Kiosk 18 and 27 have no releases yet.
