Retiring the Actions page

The Actions page is a verb list: pick a command type, pick targets, send. That matches how the server is built and not how anyone works — nobody opens the MDM wanting to "send an install_apk", they want this app on these tablets, or this kiosk locked to that app, or these screens rebooting at 4am. The nouns live on other pages, so the one page that performs the work is the one page that knows nothing about what it is working on.

What it can send today: install_apk, uninstall, shell, query, screenshot, reboot, collect_logs, wipe, unenroll — plus recipes (pins) and schedules. A refactor has to land every one of those somewhere; the mapping table at the end is how each option is checked for that.

Option A
Keep the page, group it by what you are managingcheapest

Same console, four tabs instead of one long type list: Apps · Device · Diagnostics · History. Nothing moves, nothing is retired.

Good at Every task starts from the thing it is about, which is how people describe the work. The store answers the question Actions never could — where is this app, and where is it missing — and coverage turns a send-and-hope into a number. Destructive and diagnostic verbs stop sitting one dropdown away from routine ones.

Option C
No page at all — a launcher, and objects that act on themselves

Actions disappears. Every verb lives on the noun's own page, and one keyboard launcher (the ⌘K palette already in the dock) is how you reach any of them from anywhere.

Option D
A jobs board

Keep one place for work, but make it about work in flight rather than about verbs: queued · running · finished, with a "New job" wizard. The send form becomes a wizard step, not the page's identity.

Deployed today: the single Actions console (verb list + targets + recipes), with Schedules and Manage beside it. I would ship B, with D's board as the History page. B because every task then starts from the thing it concerns and the store answers the coverage question nothing answers today; D's board because the work we just built — leases, receipts, the per-device event timeline — needs a fleet-level home, and "sent, unconfirmed 21m" belongs in a column called Needs attention rather than in a row of a history table. A is the right move if this has to be cheap this week; it is also a safe first step towards B, since the tabs are the eventual page boundaries. C I would not do alone: it makes the fleet's capabilities unteachable.

One sequencing note, if B is picked: the store's value is coverage, and coverage needs trustworthy per-device app inventory. That already exists (NeedsAppInventory, the installed-package set per device) but has never been shown fleet-wide, so the first slice should be read-only coverage — one card per app, "on N of M", drill into the missing list. If those numbers look right for a week, the Install buttons go on top of something we trust.
