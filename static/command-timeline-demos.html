"Sent" is not "received" — how command status should read

The queue shows delivered as soon as the server writes a command to a socket. A half-open socket swallows that frame, so the operator is told the device has it when the device has never seen it. The delivery query has always known this — it re-delivers anything delivered whose received_at is null — but the page never said so. That is what made AT070AABU00077 take a day: the evidence was on the screen, reading as success.

The server now records every transition in command_events (created · leased · received · progress · terminal), and received is the ack the device itself sends. Three ways to put that on the page. Pick one.

Option A
Rename the status onlyone line of work

delivered renders as Sent, and a command that has been acked shows Received. No new UI, no timeline — just stop calling an unconfirmed write a delivery.

shellAT070AABU00077 Sent3m ago
install_apkAT070AABU00231 Received2m ago
rebootAT070AABU00318 Completed1m ago
Good at Honest immediately, everywhere a status is rendered, at near-zero risk. "Sent" invites the right question where "Delivered" closed it.
Bad at Says nothing about how long it has been unconfirmed, which is the actual signal — 3 seconds at "Sent" is normal, 20 minutes is a dead socket.
Option B
Sent, with the wait called outmy pick

Option A plus the thing that distinguishes normal from broken: a command unconfirmed past its expected window turns red and says so. No timeline UI, but the page answers "is this stuck?".

shellAT070AABU00077 Sent, unconfirmed 21m21m ago
shellAT070AABU00231 Sent 4s ago4s ago
install_apkAT070AA2600030 Installing 62%2m ago
screenshotAT070AABU00318 Completed1m ago
Good at Turns the status column into a diagnosis. A red "unconfirmed 21m" next to a device the banner already calls unreachable tells the whole story without a click, and it is the exact row that would have been red on 9 Oct.
Bad at Needs a per-type notion of "too long" (the registry's lease covers it), and one more colour in a column that already carries several.
Option C
Full event timeline on the command

Everything in command_events, rendered where a single command is already shown. The gap between two events is where the answer lives, so the gap is labelled.

  • Queued by Ali Hassan · 06:03:38
  • Sent over the WebSocket · 06:03:41
  • Never received. 2h 14m with no confirmation from the device — it was checking in over HTTP the whole time, holding no socket.
  • Re-sent over its check-in · 08:17:52
  • Received by the device · 08:17:53
  • Completed · 08:17:54 · output 1 line
Good at The only option that shows where the time went, and the only one that can say "never received" as a fact rather than an inference. Free audit trail: who queued it, which transport carried it, how many attempts.
Bad at A click away, so it explains after you already suspect something. Needs a place to live (command detail page, or an expanding queue row).

Deployed today: none — the queue still says "delivered" for an unconfirmed write. I would ship B now and C next. B because it costs almost nothing and converts the status column from reassurance into a diagnosis; C because the event log is already being written and leaving it unread wastes the part of the design that answers "when did the device actually get it". A is strictly worse than B for the same work, so it only makes sense if the extra colour is unwelcome. All three are honest; only B is honest and noticeable without a click.
