Server page: where SSE streams go

The "slowest routes" table used to be topped by GET /events/devices at a p95 of 4,627,450 ms, which is 77 minutes. It wasn't slow. It was a dashboard tab left open, because an SSE stream's "duration" is how long it stayed connected. The fix now live takes streams out of that table and measures them on their own terms. The data is already in every frame as snapshot.streams. This page is about whether to show it, and how.

Three numbers carry meaning for a stream. Open now: a number that keeps climbing is a leak. Time to first byte: slow auth or a slow first query. Typical life: seconds instead of minutes means clients are reconnecting in a loop.

A. Own table under the routes Recommended

A second card called "Live streams" goes right below "Where the time goes", with the columns that matter for streams. Warning colours: time to first byte p95 over 500 ms, or a typical life under 30 s once a route has opened 20+ streams (a reconnect loop).

Good atEach table has columns that mean something for what's in it. A leak (Open keeps climbing) or a reconnect loop (short Typical life) is visible per route, which is the level you'd fix it at.
Bad atOne more card on a page that's already long. On a quiet day it's four calm rows.

D. Don't show streams Deployed now

Streams are measured and sent in the frame but not drawn. The routes table stays clean.

Good atNothing to add. The misleading numbers are already gone.
Bad atA stream leak or reconnect loop goes unnoticed until goroutines or the DB pool climb, and by then the Server page shows the symptom, not the route.

My pick: A. The point of the fix was to give each table columns that mean something. B hides the per-route answer you'd need to act on, and C brings back the mixed-meaning columns we just removed.
