Installing an app from the store

The store shows what is in the library and what is already out there. What it does not have is a way to put an app on something — today that still means leaving for a device or a device set. These are five shapes for "install", from the smallest to the one that matches how a restaurant fleet actually behaves: devices are offline half the time, so an install is rarely a thing that finishes while you watch.

A · Install button → target sheet

Every app card and the app's own page get Install. It opens one sheet: pick venues, groups or individual devices, see how many that is, send. Good: obvious, one gesture from where you already are, nothing new to learn. Bad: it is a one-shot command — the devices that are offline right now simply do not get it, and the sheet says nothing about that.

B · Install as a standing rule my pick

You do not install an app on devices, you say where this app belongs — on every kiosk, at these venues, on this group — and the server keeps that true: a device that is offline tonight gets it when it checks in, a device added to the venue next month gets it on enrolment. Same model as the client auto-update you just switched on. Good: survives the fleet being half offline, makes "who should have this" answerable, and uninstall is the same sentence in reverse. Bad: more to think about on the first install, and a rule that is wrong is wrong everywhere — so it shows the resulting device list before you save.

C · Pick the devices first, then the app

The reverse order: from Fleet you select a set of devices, and the store opens filtered to "apps these devices do not have". Good: matches a real errand — this new venue needs its four apps — and the targets are already in hand. Bad: it is a Fleet flow wearing a store's clothes; from the store itself you still need A or B.

D · Staged install, like a firmware rollout

Install reuses the rollout machinery: a canary group, then the rest, each step gated on the previous reporting healthy. Good: a bad APK stops at four devices instead of the fleet, and the vocabulary already exists on the firmware side. Bad: heavy for a 38 MB app that is usually fine, and a stalled stage needs a human.

E · One basket, one send

Tick several apps while browsing the store, then send them to one set of targets in a single step — the way you kit out a new site. Good: four apps to a new venue is one action instead of four. Bad: a basket is a mode, and a half-filled one left on the page is a trap; it only pays off on the rare "new site" day.

Pick: B, with A kept for the one-off. A standing rule is the only shape that survives a fleet where half the devices are off at any moment — the same reason the client auto-update became a policy rather than a button. A stays as the quick "put this here now" and is the smaller build, so it can ship first; C is worth adding later because it matches the new-venue errand; D only once an app install can plausibly cost a site visit.
