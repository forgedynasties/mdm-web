2 · Why the last one went, and what changes

Commit 45166d41 (30 Sep) cut Policies down to lock rules and removed the compliance page with it. That page was a flat list of fleet-wide rules, worked out live on every page load. It couldn't say since when, couldn't tell "not reported" from "fine", wasn't scoped to a venue, and nobody acted on it: no alert, no fix, no report. This plan differs on each of those points:

  • Scoped and ordered like lock rules. One fleet baseline, with a venue or group allowed to tighten or relax it. One editor, one mental model.
  • Results are stored, with history. "Non-compliant since Tuesday" and "98% compliant this week" become possible, and the customer report needs them.
  • Unknown is its own state. 166 of 194 firmware devices can't report posture. Counting them as failing would make the number meaningless; counting them as passing would be a lie.
  • Most checks use what the server already knows. Firmware line, client version, lock state, key state and last seen cover every device, including the old v2.0 ones.
  • Every check can say what to do, and some can do it: the commands already exist.

The dormant compliance_rules table and page are not revived. Its posture evaluation (and its test, TestPostureCompliance) moves into the new check registry in P1, and the old table is dropped then.

3 · The model

Check: one question with a fixed id (adb_off, firmware_current…). It knows its source (server or device), which clients can answer it, how it's evaluated, its plain-language wording for operators and for customers, and its fix if there is one.

Baseline: which checks apply, at what severity (required or recommended), and whether to auto-fix. There is one fleet baseline; overrides are scoped to a venue, group or role, ordered and resolved the way lock rules are. A device is measured against the first match per check.

Result: per device per check, one of pass fail unknown n/a, plus since and evidence (the value seen, and when). A device is compliant when no required check fails; unknowns are counted and shown, never folded into either side.

Events: a row each time a result changes (pass→fail, fail→pass). History, alerts and the report's "time to fix" all come from these.

Evaluation: on every check-in that changes a relevant key (cheap: the device's results only), plus a sweep every 5 minutes for checks that depend on time (last seen) or on server state (a new hosted build changes "client current" for everyone). New tables: compliance_overrides, compliance_results (device, check: current state) and compliance_events (transitions, pruned after 400 days). The fleet baseline lives in config, like the auto-update policy, and changes are audited (compliance.baseline).

5 · Security posture

Posture is the same results seen as exposure, not as rule-keeping. It's a fleet view and a device card, not a second engine:

  • Patch level: distribution by month across the fleet, by model and firmware line, oldest first. For our images it's one value per build, so the server can also fill it from the release record when an old client can't report it, which turns 98 unknowns into answers.
  • Debug surface: devices with USB debugging, wireless adb, developer options or a userdebug build. Wireless adb open on a venue network is the item to put first.
  • Trust chain: signing slot per device (qcom / gms / kiosk22 / dpc), own key vs shared key, keys reset and not re-registered, identity conflicts, hardware serial changes (both alerts exist already).
  • Integrity: root, verified boot, SELinux, Device Owner held.
  • Device page: the Security fold becomes Security & compliance, listing each check with pass, fail or unknown, evidence and age, and "Needs a look" takes its items from failing required checks instead of its own hand-written list.

The phase 2 client work is small: one more block in SecurityPosture.java, the same in Telemetry.kt, and a sent-on-change key list so it doesn't bloat every frame. The keys are security_patch, verified_boot, bootloader_locked, selinux, device_owner, accounts, storage_encrypted and fingerprint. All of them should be kept in device_state_events so changes are visible.

6 · Customer-facing report

The customer is the restaurant: an owner-role user scoped to their venues, or someone holding a token link, the same as the weekly PDF today. What they need is a plain statement they can file, not our internals.

Content per venue, per period (month by default):

  • Headline: "22 of 23 devices met every requirement on 30 Oct; 96% device-days compliant in October."
  • Per requirement, in customer words: Software kept up to date, Locked to the ordering app, Debug access closed, Device integrity verified, Security updates within 6 months. Each with a met / not met / not measurable count.
  • Exceptions: which device (by name and table, not serial), what was wrong, when found, when fixed, and time to fix.
  • Method and evidence: how often devices are checked, what "not measurable" means, report generated at, signed link.

Leaves out: adb, slots, keys, client versions, and anything about other venues.

Delivery: a section in the existing weekly PDF, a standalone monthly compliance PDF plus CSV of exceptions on the venue page, and a scheduled email (new: the PDF is only sent by hand today, and only to @aioapp.com). Access follows the existing grants (reportViewerFilter); access-audit.html already flags the old fleet-wide CSV, and the new one is venue-scoped from the start.

8 · Phases

P0 · decide
Answer the questions below. Demos: compliance-page-demos, compliance-baseline-demos. The dormant compliance_rules code is replaced in P1 rather than deleted now: its posture evaluation and its test carry over.
P1 · engine
Check registry, baseline + overrides, results + events tables, evaluator (on check-in + 5-minute sweep), the 8 server-side checks and the device checks already reported. /compliance page, device fold, fleet column. Done when every live device has a result for every check (pass, fail, unknown or n/a), and changing the baseline re-scores the fleet within a minute.
  • Server only, about a week. Works for all 207 devices on day one.
P2 · signals
Firmware client 1.11 and standard client 0.2.15 with the new keys; patch level filled in from the release record for our images; posture tab. Done when unknowns on posture checks fall to "only devices that can't update".
  • Client release through the usual flow (stage, pilot 022, live).
P3 · act
A compliance alert type (one per device, listing what fails, in the digest); auto-fix for the checks that have a command (USB debugging off, wireless adb off, client update, firmware OTA, lock), each off by default and audited per run.
P4 · report
Venue compliance PDF + CSV, section in the weekly PDF, scheduled email to venue contacts, owner-role access. Done when a venue owner can open last month's report from a link without seeing anything else.

9 · Decisions needed before P1

1. One baseline with overrides, or a baseline per venue?I'd go with one fleet baseline plus overrides (venue / group / role), the same shape as lock rules. A baseline per venue means 50 copies drifting apart.
2. The 98 v2.0 devices: what do they count as?I'd show them as "partly measurable": server checks apply, device checks are unknown, and the report says so. Treating them as failing would make every venue that has them look bad for something it can't change.
3. Which checks start as required?My proposal is in the catalogue column "Default". Lab and pilot devices (lab mode, the test venues) would be exempt by an override, otherwise they fill the list.
4. Auto-fix: off everywhere at first, or on for the safe ones?I'd turn on wireless-adb-off and client-update straight away (both already run unattended elsewhere), and leave the rest off until there are a few weeks of results.
5. Who gets the customer report, and how often?Owner-role users and a venue contact email, monthly, plus the section in the weekly PDF? Or on request only, for now?
6. Where does it live in the nav? answered 15 OctIts own dock entry, Compliance.
7. Patch-level threshold: 180 days as recommended, or tie it to a customer-facing promise (e.g. "security updates within 90 days")? That is a commitment AIO would be making in writing.

10 · Risks

  • A number that looks bad for reasons nobody can fix (old images, lab units). Mitigated by unknown, n/a and lab overrides; worth checking on stage with real data before any customer sees it.
  • A report is a promise. Whatever wording the customer PDF uses ("devices are kept up to date") is something AIO is now saying in writing. The wording needs a sign-off beyond engineering.
  • Auto-fix fights a technician who turned adb on to work on a device. Lab mode already marks "someone is working on this"; auto-fix should respect it.
  • Load: evaluating on every check-in across about 200 devices is trivial now. It is kept to changed keys so it stays trivial at 900.
