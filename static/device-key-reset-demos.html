Resetting a device's key

Since client 1.6.0 a firmware device registers its own key, and from then on the server refuses the shared key for it. That is the point, and it has one cost: a device that loses its key (factory reset, app data cleared) is refused too, and it raises the impersonation alert when it tries. Someone has to be able to say "that was us, let it register again". Today that is an admin API call. The options below put it on the dashboard. Figures are from live, 30 Sep: 16 firmware devices on their own key, 176 on the shared key.

Whatever is picked, the Credential row on the device page has to change: it says "Fleet device key" for every firmware device, which is now wrong for the 16.

A · The Credential row tells the truth, and Reset sits in "Careful" Recommended

The row says which key the device uses, in one of three states. The reset button goes in the Enrollment card's "Careful" band, next to Move and Retire, because it weakens the device's protection until it registers again. It opens a dialog that says exactly that and asks why. The impersonation alert that a key-less device raises gets a "Reset its key" action that opens the same dialog, since that alert is where someone will be when it happens.

The dialog

Reset the key of AT070AABU00875?

Only when the device has lost its key and is now refused. What happens:

  • The server forgets its key. The device registers a new one at its next check-in, within 5 minutes.
  • Until then, anything holding the shared key can act as this device. The shared key is public.
  • If it doesn't register within an hour, you'll get an alert.

Good at
  • The row finally says what is true, and says what to do when a device can't get a key (update the agent).
  • The reset is where the other irreversible-feeling actions are, behind a dialog that explains the risk.
  • The alert leads straight to the fix, which is where people will be when it happens.
Bad at
  • Two ways into the same dialog.
  • Settings is admin-only, so an operator who sees the alert can't reset. Deliberately: resetting weakens a device's protection.

Recommendation

A. Fix the Credential row first; it is wrong today for 16 devices. Put the reset in the "Careful" band behind a dialog that says what it weakens, and give the impersonation alert a "Reset its key" action, because a device that lost its key announces itself through that alert. Admin only. The server side already exists (POST /api/v1/devices/{serial}/key-reset); what A adds is the row, the dialog, the audit entry, and the "didn't register within an hour" alert.
