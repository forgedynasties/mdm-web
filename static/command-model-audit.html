Audit: shell, reboot, and everything else as configuration

The model you described: shell is a live session, not a job; reboot is the one imperative command; everything else is desired state declared for a set of devices — "this lot has this app", "this lot is locked to this app" — and reconciled continuously. This audit puts every command type and every existing policy mechanism against that model, says what already fits, what has to change, and what is simply broken today. Inventory is from main at 86f485b3, 13 Oct.

Imperative
Command

Happens once, now, and cannot be undone by a config. Only reboot qualifies — plus wipe and unenroll, which are terminal (see below).

Session

A live, attended connection to one device: shell, screen, logcat. Nothing is queued; if nobody is watching, nothing runs.

Declarative
Config

A rule bound to a scope. The server compares every device against it and closes the gap itself, forever — not once.

1 · What is wrong today, before the model is even applied

Two command catalogues, and they disagree. internal/command/registry.go (delivery policy: lane, lease, deadline) and internal/product/commands.go (roles, API acceptance, capability). app_reload / app_restart / app_clear_cache / app_update_check exist only in the product table and get the registry's default; config / canary / start_capture / stop_capture exist only in the registry. There is also a third list in the Actions page JS (KIND_FALLBACK, commands.html:1047) and a fourth in cmdtitle.go.
Queued commands silently die after an hour. GetPendingCommandsForDevice (db.go:5413) only hands out commands created in the last 60 minutes, whatever the registry says (installs claim a 2h deadline, OTA 6h). A device that was off for an hour never sees the install you queued, and nothing tells you.
There is no interactive shell. The page titled "Interactive shell" (device_shell.html) sends each line as a separate one-off shell command and even warns that cd does not persist. The only genuinely live path is the adb tunnel (internal/adbtunnel), which is admin-only and needs adb_tcp switched on first.
The config channel is half-built. A config command type exists in the registry and the DPC client handles it — but no server code ever creates one, and the firmware client fails it as unknown. The real config path is the WS config frame plus the check-in response. The fleet-wide device_policy (update policy, Wi-Fi/CA/VPN, managed app configs) is still merged into every check-in and still applied by the DPC client, but its UI pages were deleted in 45166d41 — it is live, un-editable state.
Scope resolution is written thirteen times. resolveTargetDeviceIDs, resolveMixedDeviceIDs, resolveScopeDeviceIDs, CommandCreate's inline switch, db.ResolveTargetIDs, resolvePolicyTargetIDs, ruleCovers, resolveEligibleDevicesUnscoped, the API's own, the access filter's own, and duplicate DB helpers (GetDeviceIDsInGroups vs GetDeviceIDsByGroupIDs). Every one snapshots to a serial list, so nothing follows membership — a device added to a group tomorrow gets nothing that was "sent to the group" today.

4 · One scope, not thirteen

A rule needs a scope that is evaluated, not snapshotted: "all", "venue X", "group G", "class kiosk", "device S" — ordered, first match wins, exactly as kiosk rules do today (ruleCovers). Every command/rule/deployment path should call one Scope.Resolve(ctx) at tick time. The shared picker then outputs a scope ({kind,id} rows) rather than a flattened serial list, with "Choose devices…" producing a device scope per pick. The thirteen resolvers collapse to that one function plus the per-device predicate.

5 · Plan

  1. Stop the bleeding (small, now). Merge the two catalogues into one (registry owns the row; product gets role/caps from it); delete config and the four lite types; make GetPendingCommandsForDevice honour the registry deadline instead of a flat hour; fix the two stale "snapshot" comments.
  2. One scope type + one resolver. Introduce Scope (ordered rows of kind/id), Resolve and Covers(device); port kiosk rules onto it (they already have this shape), then deployments (live membership), then the picker's output.
  3. App rules. New table app_rules (scope, package, version-or-latest, window, paused, by/at) and a minute job cloned from client_autoupdate.go using the coverage diff. "Install on N" on the Apps page creates a rule; the one-off install path becomes "rule with a one-device scope", so nothing is lost. Jobs shows what the rule queued.
  4. Live shell. A shell_open WS frame opens a PTY on the device (DPC: wrap the existing ShellSession; firmware: a ProcessBuilder PTY), multiplexed over the device socket exactly like start_capture; the browser side is the current SSE page turned into a terminal. Query catalog becomes a dropdown in that terminal. canary → ping_request; collect_logs → its own request frame + upload; legacy OTA probe → the same frame. Then delete the shell command type, fleet-bulk shell and scheduled shell.
  5. Settings to config. adb_tcp, mic gain, boot logo become fields in config with scopes; bring back the device_policy UI (Wi-Fi/CA/VPN, update policy, managed app configs) as rules on scopes rather than one fleet blob.
  6. Actions page → "Rules" (app rules, lock rules, firmware, settings) + a Reboot section; Jobs → reconciliation log + reboots. Schedules keep reboot only.

Order matters: 1 and 2 are prerequisites for 3; 3 is the first visible win ("this lot has this app"); 4 is independent of 3 and can run in parallel. 5 and 6 are the long tail.

6 · Decisions that are yours

Are wipe and unenroll commands, or do they go behind the enrollment flow?

They are imperative by nature. Recommendation: keep them as commands next to reboot, destructive-confirmed, so "command" means exactly "cannot be expressed as a rule". my pick: three commands

Does a one-off install still exist, or is every install a rule?

Recommendation: every install is a rule; a one-off is a rule with a single-device scope that you may delete afterwards. One code path, and the Jobs history stays complete. The user never has to know the word "rule" — the Apps page says "Install on these 36" and keeps them installed.

Does a live shell need the global shell switch and the per-device audit trail?

Today each shell line is a command row with author, time and output. A PTY loses that unless the session transcript is stored. Recommendation: store the transcript per session (who, when, device, bytes), keep the global switch, keep admin-only.

What happens to bulk screenshot and bulk shell?

Both are "run X on 40 devices and read the results" — a job, not a session. If that workflow matters, it is one legitimate exception: a bounded "run a diagnostic on a scope" that uses the query catalog only (no free text). Otherwise they go. Recommendation: keep the catalog-only diagnostic as the single exception.
