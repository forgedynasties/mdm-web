Actions · what a mixed fleet does to the console

The page was built when every device ran the system-app client. It now has to serve three agents with genuinely different powers, and it handles that with one signal: a dimmed card reading “4 of 7 can't run this on their agent — skipped at send”. You cannot see which four, the breakdown chip says only DPC (which counts MDM Lite too, since Lite is stored as a DPC kind), and the grid has a group literally called App (MDM Lite) sitting beside groups named after what the action does. Four options below. Counts are stage's real fleet: 5 firmware, 1 DPC, 1 Lite.

B · Same grid, but every card says which agents run it

The smallest change that fixes the honesty problem. The breakdown splits into three real kinds, and each card carries three badges — FW / DPC / LT — lit for the agents that can run it, greyed for the ones that cannot. Groups are renamed to what the action does, so App (MDM Lite) becomes Host app. Good: tiny diff, nothing moves, the matrix is learnable at a glance. Bad: still a count, not a list — you know the kind that will be skipped, not the serials.

C · Pick the agent first, then the action

A segmented control above the grid scopes both the selection and the actions to one agent kind, so everything on screen runs on everything selected — no dimming, no skipping, no caveats. Good: the simplest possible promise, and the grid halves in size. Bad: “reboot the whole restaurant” becomes two sends, and it makes the agent split the operator's problem when most of the time it is ours.

D · Group by coverage, and name the devices that get skipped would pick

Keep the one mixed selection, but sort the grid by how much of it an action actually reaches: Runs on all 7, Runs on some, Runs on none (collapsed). Picking a partial action replaces the caveat with the actual list — serials, grouped by why — before you send, and the Send button counts what will really happen. Good: answers the question the current page dodges, keeps mixed selections working, and the ordering means the safe actions are the ones at the top. Bad: the grid re-orders as the selection changes, so muscle memory for a card's position is weaker than in A or B.

What I would do

D, built on B's badges. The real defect is not that the page dims cards — it is that it tells you a number and then silently drops devices at send, and with three agents that now happens on most mixed selections. D turns that into a named list before the send and makes the Send button state the truth; B's per-card badges are the cheap part of it and carry the matrix. C is the tidiest page of the four, but it solves the problem by forbidding the mixed selection rather than handling it, and "reboot this restaurant" is exactly the mixed selection people will want. A stays as the fallback if we would rather not touch the grid ordering at all — in which case take B alone, which is a small diff and still removes the App (MDM Lite) category name.
