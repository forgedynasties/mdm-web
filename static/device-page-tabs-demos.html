Device page — the tab strip, especially for admins

An admin sees seven tabs: Overview · Applications · Queue · History · Alerts · About · Settings. Two of them are themselves split into sections (About: who has access, activity, hardware, software, security; Settings: enrollment, wireless adb, installed applications), and the Overview carries fourteen different action buttons. Below the strip the page is fine; the strip itself is where the crowding is. Mock serial AT070AABU00231.

Good Four tabs of equal weight. Activity = Queue + History + Alerts as one timeline with filter chips (in flight · done · alerts), which is how people actually read it: "what happened to this device, latest first". Details = About's five sections. Fourteen buttons become one grouped Actions menu, and the admin-only Settings becomes a gear + drawer, so an operator's strip and an admin's are identical. Open alerts and in-flight commands surface on the Overview rail, so folding them does not hide them.
Bad "Activity" is a merge: someone who wants only the command queue filters for it. Settings-as-drawer is a new pattern on this page (the fleet page already has one).

Recommendation

B. Seven tabs are really four jobs — what is it doing now, what runs on it, what has happened to it, what is it — and B names those four. The two things that make the admin strip crowded, the fourteen loose buttons and the admin-only Settings tab, each become one control (an Actions menu, a gear drawer), so operators and admins see the same four tabs. C if you want the merge without the drawer. D only if the page is going to keep growing sections.

Tab URLs (?tab=queue etc.) would redirect to their new homes, so bookmarks and alert links keep working.
