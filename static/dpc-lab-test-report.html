Bugs found

1Shell command wedges the WS/checkin loop High

Reproduced on rbox and KDS (permanent stall, needed a reboot to recover); D3 Pro showed the same stall but self-recovered after ~90s.
WhereCommandExecutor / ShellSession (aio-mdm-client-dpc/.../net/CommandExecutor.kt, device/ShellSession.kt)
SymptomShell command itself runs fine (ShellSession: shell session started logs, device confirmed "Enrolled" etc. earlier worked the same way) — but no further WS traffic or checkins happen afterward. No crash, no exception in logcat.
Recoveryadb force-stop is blocked by the OS for a Device-Owner-protected package ("Ignoring request to force stop protected package") — only a full reboot recovers a permanently-stalled device.
ImpactAny admin who runs a shell command against a fielded device risks silently losing checkins/remote control until someone reboots it — on something like a kiosk or menu board that could mean a trip on-site.

2Reboot command can silently no-op High

Observed on Sunmi D3 Pro — command delivery flipped to completed immediately, but last_seen_at checkins never gapped and uptime_seconds never reset. Same command genuinely rebooted the Mega kiosk (uptime 37s after, mDNS adb session dropped).
WhereCommandExecutor.reboot() — acks "completed" unconditionally before calling deviceOwner.dpm.reboot(admin), then only acks "failed" if that call throws.
Likely causeDevicePolicyManager.reboot() requires no foreground activity / keyguard shown to actually execute — if the condition isn't met, some OEM builds silently ignore the call rather than throwing, so the pre-emptive "completed" ack never gets corrected.
ImpactThe dashboard would show a reboot as having succeeded when the device never rebooted — misleading during an incident where a reboot was the intended fix.

3New device inherits a wrong device_class from the enrollment token Medium

Happened live during this session: the KDS and the first Mega-kiosk enroll attempt both got device_class: "dongle" from a token that was originally minted for the rbox, because the server only fills device_class on a device's first insert and the KDS/kiosk had no prior record.
Whereinternal/db/db.go upsert: device_class = CASE WHEN devices.device_class = '' THEN EXCLUDED.device_class ELSE devices.device_class END — correct once set, but nothing stops a mis-scoped token from setting it wrong in the first place.
Fix applied in-sessionCorrected via the dashboard's /devices/bulk-class (session-auth only, not reachable with the admin API key — see note below).
Process noteMint one enrollment profile per device class before a multi-device enroll session, not one reused token — a pre-existing device (like the D3 Pro) is safe to re-enroll with any token since its class is already set and protected, but a brand-new device is not.

4Mains-powered devices report a fake battery Medium

All 3 brand-new devices (rbox, D3 Pro, KDS) are mains-powered with no battery, but all reported a battery_pct (0%, 50%, 50%).
Client sidenet/Telemetry.kt:52 — the no-battery guard exists but trusts BatteryManager.EXTRA_PRESENT (default true); these boards' battery HAL reports present=true with a synthetic level regardless of real hardware. ui/MainActivity.kt:401 defaults the opposite way (false), so the on-device screen and the dashboard can already disagree about the same device.
Server sideinternal/product/product.go CapsForDevice only special-cases device_class == "dongle" as battery-less; pos and kds fall through to genericCaps (HasBattery: true).
DecisionDemoed 3 dashboard options (dpc-mains-power-demos.html) — picked Option B, a "Mains" chip instead of a battery number. Needs both the client default flip and the server kds/pos cap fix to be trustworthy; not yet implemented.

Process notes for future provisioning sessions

  • No camera-based QR enroll on GMS hardware — Play Protect blocks it at provisioning. adb is the only path until the DPC package is allowlisted with Google.
  • Check dumpsys device_policy | grep "Device Owner" before anything else — if it's set to a different package, a factory reset is mandatory first; if it's already aio.app.mdmclient.dpc, just reinstall/update.
  • tools/enroll-adb.sh's 20-second "confirm enrollment" check is unreliable on at least these board families — its logcat -T timestamp filter breaks when the device's own date binary doesn't support +'%m-%d %H:%M:%S.000' (seen truncating to just 10-05). The script reports failure even when enrollment succeeded. Always verify against GET /api/v1/devices/{serial} rather than trusting the script's exit message.
  • Wireless-debug (mDNS pairing) sessions do not survive a device reboot — expect to re-pair after every reboot during a lab session; a static adb tcpip 5555 session also doesn't persist across reboot on these boards.
  • Mint one enrollment profile per target device class, not a shared one, to avoid Bug 3 above.
